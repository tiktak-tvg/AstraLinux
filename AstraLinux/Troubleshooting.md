### Поиск и устранение неисправностей в Astra Linux SE
Поиск и устранение неисправностей в Astra Linux SE требует системного подхода и знания специфики защищённой ОС. Ниже — методология, ключевые сценарии и практические шаги для восстановления системы.

#### Методология поиска и устранения неисправностей
Эффективный поиск неисправностей строится на последовательном анализе и классификации проблем. В курсе AL-1806 от «Группы Астра» выделяются следующие категории неисправностей:

- Восстановление загрузки системы: проблемы с загрузчиком, ядром, загрузочным носителем.
- Проблемы с ПО: сбои после установки или обновления пакетов.
- Проблемы с устройствами хранения: логические сбои ФС, ошибки монтирования, повреждение таблицы разделов.
- Проблемы безопасности: диагностика и настройка безопасной работы.
- Сетевые неисправности: проверка работоспособности сети и локализация проблем.

Общий алгоритм диагностики:

- Сбор информации: анализ системных журналов (journalctl, /var/log/syslog), вывод команд dmesg, systemctl status.
- Локализация: определение стадии, на которой возникает сбой (загрузчик, ядро, монтирование ФС, запуск служб).
- Принятие решения: выбор метода восстановления — от корректировки конфигурации до полной переустановки компонента.
- Проверка: тестирование системы после внесённых изменений.

#### Решение проблем, связанных с нештатными и аварийными перезагрузками
Аварийные перезагрузки часто приводят к циклическим сбоям или ошибкам файловой системы. Один из типичных сценариев — некорректное системное время, вызывающее ошибку суперблока.

Симптом: при загрузке появляется сообщение вида:

```text
/dev/sda1: Superblock last mount time (...) is in the future.
```
Причина: системное время в BIOS отстаёт от реального (например, из-за севшей батарейки CMOS) или было вручную переведено на будущую дату и обратно.

Решение:

Войти в меню настройки BIOS/UEFI и проверить системное время. При необходимости заменить элемент питания на системной плате и установить корректное время.

Если время в BIOS верное, но циклическая перезагрузка продолжается:

Установить в BIOS время на будущую дату (позже указанной в ошибке).

Загрузить ОС.

Создать файл ``/etc/e2fsck.conf`` с содержимым:
```text
[options]
broken_system_clock = true
```
Создать hook-скрипт ``/etc/initramfs-tools/hooks/e2fsck-conf.sh`` для копирования конфигурации в ``initramfs``.

Выполнить sudo update-initramfs -u и перезагрузиться.

После загрузки установить текущее время.

#### Устранение неисправностей на начальных стадиях загрузки
Начальная стадия включает работу загрузчика GRUB и загрузку ядра. Основные проблемы — повреждение загрузчика, отсутствие файлов в /boot или ошибки монтирования корневой ФС.

Восстановление загрузчика GRUB

Если система не загружается и появляется приглашение grub rescue>, необходимо восстановить загрузчик. Способ через режим восстановления с установочного диска:

 - Загрузиться с инсталляционного диска (USB) Astra Linux и выбрать «Режим восстановления».
 - Выбрать корневой раздел (например, /dev/sda1 или LVM-том) и запустить оболочку в нём.
 - Перейти в псевдотерминал ``(Ctrl+Alt+F2)``, нажать ``Enter`` и выполнить:

```bash
chroot /target
```
Убедиться, какой пакет GRUB установлен (grub-pc для Legacy BIOS, grub-efi-amd64 для UEFI).

Выполнить установку загрузчика:

```bash
# Для Legacy BIOS
grub-install /dev/sda
# Для UEFI
grub-install --target=x86_64-efi --efi-directory=/boot/efi --bootloader-id=astralinux
```
Обновить конфигурацию: update-grub.

> Важно: Для UEFI-систем команда ``grub-install`` требует указания каталога EFI и идентификатора загрузчика.

Работа с каталогом ``/boot``

Неудачное обновление ядра при нехватке места в ``/boot`` — частая причина отказа загрузки. Симптом: ошибка о невозможности загрузить ядро или отсутствии ``initrd``.

Решение через режим восстановления:

- Загрузиться в режиме восстановления и выполнить ``chroot /target``.
- Резервное копирование (необязательно): ``cp -r /boot/ /home/boot-backup``.
- Освобождение места: удалить старые версии ядра ``(rm /boot/vmlinuz-*, rm /boot/initrd.img-*)``, оставив только текущую рабочую версию.

Перегенерация ``initrd`` для текущего ядра:
```bash
update-initramfs -u -k $(uname -r)
Обновить GRUB: update-grub.
```
#### Устранение неисправностей на заключительных стадиях загрузки
Заключительная стадия — запуск systemd и служб. Типичные проблемы: зависание на этапе запуска служб, ошибки в fstab, недоступность графической оболочки.

Диагностика:

- Загрузиться в режиме восстановления.
- Проверить журналы: journalctl -b -p err (ошибки текущей загрузки).
- Проверить состояние служб: systemctl --failed.
- Проверить корректность /etc/fstab: mount -a (все ФС должны монтироваться без ошибок).
- При проблемах с графикой проверить журнал Xorg: cat /var/log/Xorg.0.log | grep EE.
- Восстановление доступа к системе:

- Сброс пароля администратора. Если пароль GRUB2 известен, можно загрузиться в однопользовательском режиме: В меню GRUB нажать e.
- В строке, начинающейся с linux, заменить ro quiet splash на rw, добавить init=/bin/bash.
- Нажать F10. После загрузки в оболочку выполнить:

```bash
passwd <имя_пользователя>
faillog -r   # сброс счётчика неудачных попыток
/sbin/reboot -f
```
Если пароль GRUB неизвестен — загрузиться с установочного диска, выбрать «Режим восстановления», выполнить chroot /target и сбросить пароль.<br>
Если учётная запись администратора заблокирована (дата окончания срока действия пароля — 0), отредактировать /etc/shadow, удалив это значение для нужного пользователя.

#### Подготовка дампа для отправки разработчикам
По умолчанию в Astra Linux сохранение дампов памяти процессов запрещено (значение ulimit -S -c равно 0). Для сбора дампа необходимо:

Разрешить дампы временно (до перезагрузки):
```bash
ulimit -S -c unlimited
```
Разрешить постоянно: добавить в /etc/security/limits.conf строку:
```text
* soft core unlimited
```
и перезагрузить систему.

Указать место сохранения дампов (например, в домашнем каталоге):
```bash
echo "/home/$USER/astra-dump" | sudo tee /proc/sys/kernel/core_pattern
```
Воспроизвести сбой: запустить проблемное приложение и дождаться аварийного завершения. В указанном каталоге появится файл дампа (например, astra-dump или core).

Собрать сопроводительную информацию: версия ОС ``(cat /etc/astra_version)``, версия ядра ``(uname -a)``, вывод ``journalctl -b`` на момент сбоя, конфигурационные файлы проблемного ПО.

#### Практическая работа
Цель: Восстановить загрузчик, сбросить пароль администратора, собрать дамп и продемонстрировать восстановление /boot.

##### Шаг 1. Восстановление загрузчика GRUB (сценарий UEFI)
Загрузиться с установочного диска Astra Linux, выбрать «Режим восстановления».

Выбрать корневой раздел (например, ``/dev/sda2 для UEFI-системы``), запустить оболочку.

Перейти в консоль ``(Ctrl+Alt+F2)``, выполнить ``chroot /target``.

Смонтировать EFI-раздел, если он не смонтирован:
```bash
mount /dev/sda1 /boot/efi
```
Переустановить GRUB:
```bash
grub-install --target=x86_64-efi --efi-directory=/boot/efi --bootloader-id=astralinux
update-grub
```
Перезагрузиться, извлечь установочный носитель.

##### Шаг 2. Восстановление пароля администратора
В меню GRUB нажать e, отредактировать строку linux: заменить ro quiet splash на rw, добавить init=/bin/bash.

Нажать F10, дождаться приглашения root@(none):/#.

Выполнить:
```bash
passwd <имя_администратора>
faillog -r
/sbin/reboot -f
```
##### Шаг 3. Подготовка дампа
Разрешить дампы:
```bash
echo '* soft core unlimited' | sudo tee -a /etc/security/limits.conf
```
Перезагрузиться.

Указать место сохранения дампов:
```bash
echo "/home/$USER/dumps/core" | sudo tee /proc/sys/kernel/core_pattern
```
Смоделировать сбой:
```bash
sleep 20 &
killall -11 sleep
```
Проверить наличие дампа в ``/home/$USER/dumps/``.

##### Шаг 4. Восстановление каталога /boot
- Загрузиться в режиме восстановления, выполнить ``chroot /target``.
- Проверить содержимое ``/boot: ls -la /boot``.
- Удалить ненужные версии ядра и ``initrd``.
- Перегенерировать ``initrd`` для текущего ядра:

```bash
update-initramfs -u -k $(uname -r)
update-grub
```
#### Ключевые особенности Astra Linux SE
- Режим восстановления — основной инструмент для решения проблем с загрузкой. В нём доступна только консоль, все действия выполняются от ``root без sudo``.
- Мандатный контроль (МКЦ) в Special Edition может ограничивать доступ к некоторым журналам и командам. Для операций восстановления может потребоваться высокий уровень целостности.
- Специфика UEFI: Команды восстановления GRUB для UEFI требуют явного указания ``--target и --efi-directory``.
- Ограничение дампов: По умолчанию дампы отключены — это мера безопасности, которую нужно осознанно ослаблять при диагностике.
