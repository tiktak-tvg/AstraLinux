### Архитектура PostgreSQL
#### 1. Общее устройство PostgreSQL
PostgreSQL построен по клиент-серверной модели. Клиент (psql, pgAdmin, приложение) подключается к серверу по протоколу libpq, сервер обрабатывает запросы и возвращает результат.

Основные процессы

Процесс             |	Назначение
------------------- | -------------------------
Postmaster (postgres)	 | Родительский процесс. Слушает порт, принимает подключения, порождает backend-процессы
Backend (postgres)	 | Обслуживает одно клиентское соединение: разбирает SQL, выполняет запросы, возвращает результат
Background writer	 | Периодически сбрасывает «грязные» страницы из shared buffers на диск
Checkpointer	 | Выполняет контрольные точки: сбрасывает все грязные страницы и фиксирует позицию в WAL
WAL writer	 | Записывает WAL-буферы на диск
Autovacuum launcher/workers	 | Запускает автоматическую очистку и анализ таблиц
Archiver	 | Копирует завершённые WAL-сегменты в архив (при archive_mode = on)
Stats collector	 | Собирает статистику по запросам и таблицам
Logical replication launcher	 | Запускает процессы логической репликации

Память
Shared memory — общая память всех процессов:
- shared_buffers — кэш страниц данных (обычно 25% ОЗУ);
- wal_buffers — буфер журнала предзаписи;
- блокировки, пул подключаемых процессов и др.
- Local memory — память backend-процесса:
- work_mem — для сортировок и хеш-таблиц;
- maintenance_work_mem — для VACUUM, CREATE INDEX;
- temp_buffers — для временных таблиц.

Файловая структура (PGDATA)
```text
PGDATA/
├── base/               # данные баз (по OID)
├── global/             # общесистемные таблицы (pg_database и др.)
├── pg_wal/             # журналы предзаписи (WAL)
├── pg_xact/            # статусы транзакций
├── pg_multixact/       # мультитранзакции
├── pg_tblspc/          # ссылки на табличные пространства
├── postgresql.conf     # конфигурация
├── pg_hba.conf         # аутентификация
└── PG_VERSION          # версия кластера
```
Схема взаимодействия
```text
Клиент → Postmaster → Backend → Shared Buffers / WAL Buffers → Диск
```
Backend читает страницы из shared_buffers. Если страницы нет — загружает с диска. Изменения сначала попадают в WAL, затем в страницы в памяти. Сброс на диск выполняют background writer и checkpointer.

#### 2. Изоляция и многоверсионность (MVCC)
MVCC (Multiversion Concurrency Control) — механизм, при котором каждая транзакция видит согласованный снимок данных на определённый момент времени. Читатели не блокируют писателей, писатели не блокируют читателей.

Как работает MVCC
Каждая версия строки хранит служебные поля:
- xmin — XID транзакции, создавшей версию;
- xmax — XID транзакции, удалившей или обновившей версию;
- cid, ctid, infomask — вспомогательная информация.
- При UPDATE создаётся новая версия строки, старая помечается как мёртвая (xmax).
- При DELETE строка помечается как удалённая (xmax), физически не удаляется.
- VACUUM удаляет мёртвые версии и освобождает место.

Уровни изоляции

Уровень             |	Грязное чтение  | Неповторяющееся чтение  | Фантомное чтение  | Потерянные обновления
------------------- | ----------------- | ----------------- | -------------- | ---------------------------------
READ COMMITTED (по умолчанию)	 | Нет	 | Да	 | Да	 | Да
REPEATABLE READ   	 | Нет	 | Нет	 | Нет	 | Нет
SERIALIZABLE	 | Нет	 | Нет	 | Нет	 | Нет

- READ COMMITTED — каждый оператор видит снимок на момент начала оператора.
- REPEATABLE READ — транзакция видит снимок на момент первого запроса. В PostgreSQL это snapshot isolation, предотвращает фантомное чтение, но возможны аномалии сериализации (write skew).
- SERIALIZABLE — использует SSI (Serializable Snapshot Isolation), гарантирует полную сериализуемость. Может завершаться ошибкой сериализации, которую клиент должен повторить.

> Важно: в PostgreSQL нет уровня READ UNCOMMITTED — он ведёт себя как READ COMMITTED.

3. Буферный кэш и журнал

Буферный кэш (shared_buffers)
- Хранит страницы данных размером 8 КБ.
- Ускоряет доступ: если страница в кэше — чтение с диска не требуется.
- Управляется алгоритмом Clock Sweep (вытеснение давно неиспользуемых страниц).
- Для массовых операций (VACUUM, COPY) используется кольцевой буфер, чтобы не вытеснять полезные страницы.
- Эффективность оценивается через hit ratio (доля попаданий).

Журнал предзаписи (WAL)
- WAL (Write-Ahead Log) — журнал, в который записываются все изменения до их применения к файлам данных. Принцип: сначала WAL, потом данные.
- WAL-буферы (wal_buffers) накапливают записи.
- WAL writer сбрасывает их на диск.
- Сегменты WAL имеют размер 16 МБ (по умолчанию).
- При коммите транзакции WAL-запись должна быть сброшена на диск (если synchronous_commit = on).

Зачем нужен WAL:
- Восстановление после сбоя (crash recovery).
- Восстановление на момент времени (PITR) с помощью архива WAL.
- Физическая и логическая репликация.

Контрольные точки (checkpoints)
- Checkpointer периодически выполняет контрольную точку: сбрасывает все грязные страницы на диск и фиксирует позицию в WAL.
- После сбоя восстановление начинается с последней контрольной точки.
- Параметры: checkpoint_timeout, max_wal_size, checkpoint_completion_target.

Восстановление
- Crash recovery — при запуске после сбоя PostgreSQL читает WAL с последней контрольной точки и применяет изменения.
- PITR — восстановление из базовой копии + архив WAL до нужной точки.

4. Взаимодействие компонентов (пример)
- Клиент отправляет UPDATE employees SET salary = salary + 1000 WHERE id = 1.
- Backend находит страницу в shared_buffers (или загружает с диска).
- Создаётся новая версия строки, старая помечается мёртвой.
- Изменение записывается в WAL-буферы.
- При коммите WAL writer сбрасывает WAL на диск.

Background writer/checkpointer позже сбрасывает изменённые страницы на диск.

VACUUM со временем удаляет мёртвую версию.
