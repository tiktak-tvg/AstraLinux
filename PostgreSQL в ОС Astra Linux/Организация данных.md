#### В PostgreSQL данные организованы на двух взаимосвязанных уровнях: логическом (как объекты видны пользователю и приложениям) и физическом (как эти объекты хранятся на диске). Понимание этой двухуровневой модели — ключ к эффективному администрированию СУБД.

#### Логическая структура
Логическая структура описывает иерархию объектов, с которыми работает пользователь. Она не зависит от физического размещения файлов на диске. Верхним уровневым понятием является кластер баз данных — совокупность всех баз данных, управляемых одним экземпляром сервера PostgreSQL.

Внутри кластера выделяются три основные сущности:
- Базы данных (Databases): Каждая база данных — это изолированное пространство имён. Подключившись к одной базе, вы не можете напрямую обращаться к объектам другой базы в рамках одного соединения. Базы данных содержат все остальные объекты.
- Роли (Roles): Глобальные пользователи и группы, которые существуют на уровне всего кластера и могут подключаться к любым базам данных, если имеют на это права.
- Табличные пространства (Tablespaces): Хотя это и логическое имя, оно напрямую связано с физическим размещением, о чём будет сказано ниже.
- Внутри базы данных объекты организованы с помощью схем (Schemas). Схема — это логическая группа объектов, таких как таблицы, представления, индексы, функции и последовательности. Схемы позволяют:
- Организовать объекты по функциональному признаку (например, sales, hr, reporting).
- Избежать конфликтов имён: в разных схемах могут существовать таблицы с одинаковыми именами.
- Управлять правами доступа на уровне группы объектов.
- По умолчанию в PostgreSQL используется схема public. Полное имя объекта в PostgreSQL состоит из имени схемы и имени самого объекта, например sales.orders.

#### Физическая структура
Физическая структура описывает, как логические объекты (таблицы, индексы) отображаются в файлы на диске. Это реализация, скрытая от пользователя, но важная для администратора.

Табличные пространства (Tablespaces) как основа физической организации
- Табличные пространства — это средство для организации физического хранения данных, которое определяет расположение данных в файловой системе. Они позволяют администратору:
- Размещать разные объекты на разных физических дисках (например, «горячие» данные на SSD, а архивные — на HDD).
- Управлять дисковым пространством более гибко.
- При инициализации кластера создаются два табличных пространства по умолчанию:
- pg_default: Расположено в $PGDATA/base. Здесь по умолчанию хранятся все пользовательские базы данных и объекты.
- pg_global: Расположено в $PGDATA/global. Здесь хранятся объекты системного каталога, общие для всего кластера.
- Пользовательское табличное пространство можно создать в любом каталоге файловой системы командой CREATE TABLESPACE. PostgreSQL создаст символическую ссылку на этот каталог в $PGDATA/pg_tblspc/. Важно понимать, что, несмотря на внешнее расположение, табличные пространства являются неотъемлемой частью кластера.

Файлы, страницы и кортежи

Внутри табличного пространства каждый объект (таблица, индекс) хранится в отдельном файле (или наборе файлов, если объект превышает 1 ГБ). Файлы данных разбиты на страницы (pages) фиксированного размера, обычно 8 КБ.

Страница — это основная единица чтения и записи данных. Её структура включает:
- Заголовок страницы (PageHeaderData): Содержит служебную информацию, такую как указатели на свободное пространство и позиции в WAL.
- Массив указателей на элементы (ItemIdData): Набор пар (смещение, длина), которые указывают на фактические данные на странице.
- Свободное пространство (Free space): Неразмеченная область для новых данных.
- Элементы (Items): Сами данные. В таблице элемент — это строка (кортеж), в индексе — запись индекса.
- Ключевое ограничение архитектуры PostgreSQL: кортеж (строка) не может занимать несколько страниц. Он должен целиком помещаться в одну страницу.

Механизм TOAST (The Oversized-Attribute Storage Technique)
- Для хранения строк, которые слишком велики, чтобы поместиться на одной странице (например, из-за больших текстовых полей или JSON), используется механизм TOAST.
- Порог: Если размер кортежа превышает TOAST_TUPLE_THRESHOLD (обычно 2 КБ), запускается механизм TOAST.
- Сжатие и вынос: Большие значения атрибутов сжимаются. Если после сжатия строка всё ещё слишком велика, «тяжёлые» значения выносятся в специальную TOAST-таблицу, связанную с основной таблицей. В основной строке остаётся только небольшой указатель на эти данные.
- Прозрачность: Для пользователя и приложений этот процесс полностью прозрачен: при выборке PostgreSQL автоматически «собирает» исходное значение из основной строки и TOAST-таблицы.
