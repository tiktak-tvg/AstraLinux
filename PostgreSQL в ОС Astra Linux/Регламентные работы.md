### Регламентные работы в PostgreSQL (Astra Linux Special Edition)
#### 1. Возможности команды VACUUM
*VACUUM* — это команда PostgreSQL, выполняющая сборку мусора и, опционально, анализ базы данных. В нормальном режиме работы PostgreSQL кортежи, удалённые или устаревшие в результате обновления, не удаляются физически из таблицы — они остаются там до выполнения VACUUM.

Зачем нужен VACUUM:
- VACUUM необходимо регулярно обрабатывать каждую таблицу по нескольким причинам:
- Восстановление или повторное использование дискового пространства, занимаемого обновлёнными или удалёнными строками.
- Обновление статистики данных, используемой планировщиком запросов PostgreSQL.
- Обновление карты видимости, которая ускоряет только индексные сканирования.
- Защита от потери очень старых данных из-за зацикливания идентификаторов транзакций (XID) или мультитранзакций.

Два варианта VACUUM:

Вариант                 | Описание                              | Блокировка
----------------------- | ------------------------------------- | -------------
VACUUM (стандартный)	 | Просто освобождает пространство и делает его доступным для повторного использования внутри той же таблицы.  | Может выполняться параллельно с обычным чтением и записью таблицы. Не возвращает место операционной системе (в большинстве случаев)	Не требует эксклюзивной блокировки
VACUUM FULL	 | Перезаписывает всё содержимое таблицы в новый дисковый файл без лишнего пространства, позволяя вернуть неиспользуемое место операционной системе.  | Работает намного медленнее и требует блокировки ACCESS EXCLUSIVE на каждой таблице во время обработки	ACCESS EXCLUSIVE
VACUUM FULL также требует дополнительного дискового пространства, поскольку записывает новую копию таблицы и не освобождает старую до завершения операции. Обычно его следует использовать только тогда, когда из таблицы нужно освободить значительный объём пространства.

Синтаксис VACUUM:

sql
VACUUM [ ( option [, ...] ) ] [ table_and_columns [, ...] ]

VACUUM [ FULL ] [ FREEZE ] [ VERBOSE ] [ ANALYZE ] [ table_and_columns [, ...] ]
Без списка table_and_columns VACUUM обрабатывает каждую таблицу и материализованное представление в текущей базе данных, на которые у текущего пользователя есть разрешение. С списком — только указанные таблицы. VACUUM ANALYZE выполняет VACUUM, а затем ANALYZE для каждой выбранной таблицы — это удобная комбинация для скриптов регулярного обслуживания.

Основные параметры VACUUM:

Параметр	Описание
FULL	Выбирает «полную» очистку, которая может освободить больше места, но занимает гораздо больше времени и эксклюзивно блокирует таблицу
FREEZE	Выбирает агрессивное «замораживание» кортежей. Эквивалентно выполнению VACUUM со значениями vacuum_freeze_min_age и vacuum_freeze_table_age, равными нулю
VERBOSE	Выводит подробный отчёт о действиях VACUUM для каждой таблицы
ANALYZE	Обновляет статистику, используемую планировщиком для определения наиболее эффективного способа выполнения запроса
DISABLE_PAGE_SKIPPING	Обычно VACUUM пропускает страницы на основе карты видимости. Эта опция отключает такое поведение
SKIP_LOCKED	Указывает, что VACUUM не должен ждать снятия блокировок с отношениями, которые не может заблокировать немедленно
INDEX_CLEANUP { AUTO | ON | OFF }	Управляет тем, пытается ли VACUUM удалить мёртвые записи индексов
PROCESS_MAIN	Определяет, должен ли VACUUM обрабатывать основную таблицу
PROCESS_TOAST	Определяет, должен ли VACUUM обрабатывать TOAST-таблицу
TRUNCATE	Указывает, что VACUUM должен попытаться обрезать пустые страницы в конце таблицы, чтобы освободившееся место было возвращено операционной системе
PARALLEL integer	Указывает количество фоновых рабочих процессов для параллельной очистки индексов
SKIP_DATABASE_STATS	Пропускает обновление статистики базы данных
ONLY_DATABASE_STATS	Обновляет только статистику базы данных
BUFFER_USAGE_LIMIT size	Устанавливает размер буфера для кольцевого буфера

При заключении списка опций в скобки опции можно записывать в любом порядке. Без скобок опции должны быть указаны точно в порядке, показанном выше. Синтаксис со скобками был добавлен в PostgreSQL 9.0; синтаксис без скобок устарел.

#### 2. Регулирование нагрузки в процессе очистки
VACUUM может создавать значительную нагрузку на систему ввода-вывода. Для регулирования этой нагрузки PostgreSQL использует механизм стоимости (cost-based) ограничения.

Принцип работы:

При выполнении операций VACUUM PostgreSQL использует внутренний счётчик для отслеживания оценочной стоимости различных операций ввода-вывода. Когда счётчик достигает значения, указанного параметром cost limit, выполняющий операцию процесс засыпает на короткий промежуток времени, указанный параметром cost delay. Затем счётчик сбрасывается, и работа продолжается.

Параметры для ручного VACUUM:

Параметр	Описание	Значение по умолчанию
vacuum_cost_delay	Время (в миллисекундах), на которое процесс VACUUM засыпает при достижении предела стоимости. Значение 0 отключает механизм ограничения	0
vacuum_cost_limit	Порог, при котором процесс VACUUM засыпает. Представляет собой накопленную оценочную стоимость дополнительных операций ввода-вывода. Увеличение значения уменьшает количество событий ожидания Timeout:VacuumDelay	200

Параметры для autovacuum:

Параметр	Описание	Значение по умолчанию
autovacuum_vacuum_cost_delay	Значение задержки стоимости для автоматических операций VACUUM. Установка значения 0 отключает механизм ограничения	2 мс
autovacuum_vacuum_cost_limit	Значение предела стоимости для автоматических операций VACUUM. Если задано -1, autovacuum использует значение vacuum_cost_limit	-1

Рекомендации по настройке:
- Увеличение значений cost limit позволяет VACUUM использовать больше ресурсов перед переходом в спящий режим, что уменьшает количество событий ожидания Timeout:VacuumDelay.
- Увеличение значений cost delay делает события ожидания Timeout:VacuumDelay более частыми и продолжительными.
- Параметр autovacuum_max_workers также влияет на количество событий Timeout:VacuumDelay: каждый дополнительный рабочий процесс autovacuum способствует более быстрому достижению предела стоимости, что приводит к более частому срабатыванию задержки.

#### 3. Параллельная очистка индексов
Начиная с PostgreSQL 12, VACUUM поддерживает параллельную очистку индексов с использованием нескольких фоновых рабочих процессов.

Синтаксис:

sql
VACUUM (PARALLEL 4) table_name;
Параметр PARALLEL integer указывает количество фоновых рабочих процессов для выполнения этапов очистки и уборки индексов. Эта функция известна как parallel vacuum. Чтобы отключить эту функцию, можно использовать опцию PARALLEL и указать количество рабочих процессов, равное нулю.

Особенности параллельной очистки:
- Параллельная очистка применяется только к этапам очистки индексов; основная таблица обрабатывается последовательно.
- Число рабочих процессов для одной базы данных не ограничивается, при этом каждый процесс старается не повторять работу, только что выполненную другими.
- В ограничениях max_connections или superuser_reserved_connections число выполняющихся рабочих процессов не учитывается.
- Параллельная автоочистка (parallel autovacuum) находится в экспериментальной фазе и предназначена только для тестирования.

Пример использования:

sql
-- Параллельная очистка таблицы с 4 рабочими процессами
VACUUM (PARALLEL 4, VERBOSE) big_table;

-- Параллельная очистка с анализом
VACUUM (PARALLEL 4, ANALYZE) big_table;

#### 4. Команды для оптимизации данных: CLUSTER, REINDEX, TRUNCATE
##### 4.1. CLUSTER
CLUSTER указывает PostgreSQL кластеризовать таблицу, заданную параметром table_name, согласно индексу, заданному параметром index_name. Указанный индекс уже должен быть определён в таблице. При кластеризации таблица физически переупорядочивается на основе информации индекса.

Синтаксис:

sql
CLUSTER [VERBOSE] table_name [ USING index_name ]
CLUSTER [VERBOSE]

Особенности:
- Кластеризация — это одноразовая операция: при последующем обновлении таблицы изменения не кластеризуются, то есть не предпринимается попытка сохранить новые или обновлённые строки в соответствии с их индексным порядком. При желании можно периодически повторять кластеризацию, снова выдавая команду.
- Запоминание индекса: при кластеризации таблицы PostgreSQL запоминает, по какому индексу она была кластеризована. Форма CLUSTER table_name повторно кластеризует таблицу, используя тот же индекс, что и раньше.
- Блокировка: при кластеризации таблицы на неё устанавливается блокировка ACCESS EXCLUSIVE. Это предотвращает любые другие операции с базой данных (как чтение, так и запись) на таблице до завершения CLUSTER.
- Требования к дисковому пространству: при использовании индексного сканирования создаётся временная копия таблицы, содержащая данные в порядке индекса, а также временные копии каждого индекса таблицы. Поэтому необходимо свободное место на диске, как минимум равное сумме размера таблицы и размеров индексов.

Примеры:

sql
-- Кластеризовать таблицу employees по индексу employees_ind
CLUSTER employees USING employees_ind;

-- Повторно кластеризовать таблицу employees, используя тот же индекс, что и раньше
CLUSTER employees;

-- Кластеризовать все ранее кластеризованные таблицы в текущей базе данных
CLUSTER;

##### 4.2. REINDEX
REINDEX восстанавливает индекс с использованием данных, хранящихся в таблице индекса, заменяя старую копию индекса. Команда помогает поддерживать согласованную производительность базы данных.

Синтаксис:

sql
REINDEX [ ( option [, ...] ) ] { INDEX | TABLE | SCHEMA | DATABASE | SYSTEM } name
Примеры:

sql
-- Перестроить один индекс
REINDEX INDEX my_index;

-- Перестроить все индексы таблицы
REINDEX TABLE my_table;

-- Перестроить все индексы в схеме
REINDEX SCHEMA my_schema;

-- Перестроить с опцией CONCURRENTLY (не блокирует чтение и запись)
REINDEX INDEX CONCURRENTLY my_index;
REINDEX TABLE CONCURRENTLY my_table;

Опция CONCURRENTLY (доступна с PostgreSQL 12):
- Позволяет перестроить индекс без блокировки чтения или записи таблицы, а также без блокировки запросов, использующих этот индекс.
- Однако при использовании этой опции завершение процесса занимает больше времени.
- Когда выполнять REINDEX:
- При выполнении большого количества DML-операций над таблицей возникает раздувание (bloat) таблиц и индексов. Индексы используются для ускорения поиска, и их раздувание влияет на производительность поиска и запросов. Поэтому рекомендуется перестраивать индексы для таблиц с интенсивными DML-операциями, чтобы обеспечить согласованную производительность запросов.

##### 4.3. TRUNCATE
TRUNCATE быстро удаляет все строки из таблицы. Команда не выполняет никаких пользовательских триггеров ON DELETE, которые могут существовать для таблицы.

Синтаксис:

sql
TRUNCATE [ TABLE ] [ ONLY ] name [ * ] [, ... ]
    [ RESTART IDENTITY | CONTINUE IDENTITY ] [ CASCADE | RESTRICT ]

Особенности:
- Ссылки по внешнему ключу: TRUNCATE нельзя использовать для таблицы, на которую есть ссылки по внешнему ключу из других таблиц, если только все такие таблицы не будут также усечены в той же команде. Проверка достоверности в таких случаях потребовала бы сканирования таблиц, а весь смысл операции — не делать этого. Опция CASCADE может использоваться для автоматического включения всех зависимых таблиц, но при использовании этой опции нужно быть очень осторожным, иначе можно потерять данные, которые не планировалось удалять!
- Триггеры: TRUNCATE не запускает никакие триггеры ON DELETE, которые могут существовать для таблиц. Но он запускает триггеры ON TRUNCATE. Если для каких-либо таблиц определены триггеры ON TRUNCATE, то все триггеры BEFORE TRUNCATE срабатывают до любого усечения, а все триггеры AFTER TRUNCATE срабатывают после последнего усечения и сброса любых последовательностей.
- MVCC-безопасность: TRUNCATE не является MVCC-безопасным. После усечения таблица будет выглядеть пустой для параллельных транзакций, если они используют снимок, сделанный до усечения.
- Транзакционная безопасность: TRUNCATE безопасен с точки зрения данных в таблицах: усечение будет безопасно откатано, если окружающая транзакция не будет зафиксирована.
- Блокировка: TRUNCATE требует блокировки ACCESS EXCLUSIVE на таблице перед удалением содержимого.

Примеры:

sql
-- Усечь таблицы bightable и fattable
TRUNCATE bightable, fattable;

-- То же самое, но также сбросить связанные генераторы последовательностей
TRUNCATE bightable, fattable RESTART IDENTITY;

-- Усечь таблицу othertable и каскадно применить к таблицам, ссылающимся на неё
TRUNCATE othertable CASCADE;

#### 5. Предотвращение переполнения счетчика транзакций
Проблема зацикливания XID:

Семантика транзакций MVCC в PostgreSQL зависит от возможности сравнения номеров идентификаторов транзакции (XID): версия строки с XID вставки больше текущего XID транзакции находится в «будущем» и не должна быть видна текущей транзакции. Но поскольку идентификаторы транзакций имеют ограниченный размер (32 бита), кластер, который работает долгое время (более 4 миллиардов транзакций), будет страдать от оборачивания идентификатора транзакции: счётчик XID оборачивается до нуля, и все транзакции, которые были в прошлом, кажутся находящимися в будущем — это означает, что их вывод становится невидимым. Короче говоря, катастрофическая потеря данных.

Решение — замораживание через VACUUM:
- Чтобы этого избежать, необходимо периодически выполнять очистку каждой таблицы в каждой базе данных хотя бы один раз каждые два миллиарда транзакций. Причина того, что периодическое выполнение очистки решает проблему, заключается в том, что VACUUM пометит строки как замороженные, указывая, что они были вставлены транзакцией, которая была завершена достаточно давно, чтобы эффекты вставляющей транзакции были наверняка видны всем текущим и будущим транзакциям.
- PostgreSQL резервирует специальный XID, FrozenTransactionId, который не подчиняется обычным правилам сравнения XID и всегда считается старше любого нормального XID. Замороженные версии строк рассматриваются так, как будто вставляющий XID был равен FrozenTransactionId, поэтому они будут казаться «в прошлом» для всех обычных транзакций независимо от проблем с оборачиванием.

Параметры управления замораживанием:

Параметр	Описание
vacuum_freeze_min_age	Любой XID старше этого количества транзакций заменяется на FrozenXID. Большие значения сохраняют транзакционную информацию дольше, меньшие значения увеличивают количество транзакций, которые могут пройти до необходимости повторной очистки таблицы
vacuum_freeze_table_age	Если значение relfrozenxid для таблицы старше этого количества транзакций, производится агрессивная очистка с целью замораживания
autovacuum_freeze_max_age	Если таблица может содержать XID старше указанного возраста, запускается autovacuum для замораживания (даже если autovacuum отключён)

Предупреждения сервера:

Сервер выдаёт предупреждения, когда счётчик транзакций приближается к точке оборачивания. Если счётчик становится слишком близко к оборачиванию, сервер прекращает принимать запросы. Это гарантирует, что данные не будут потеряны до выполнения необходимой очистки. Существует запас безопасности в 1 миллион транзакций, позволяющий администратору восстановиться без потери данных, вручную выполнив необходимые команды VACUUM.

Мониторинг возраста XID:

sql
-- Просмотр возраста XID для таблиц
SELECT c.oid::regclass as table_name,
       greatest(age(c.relfrozenxid), age(t.relfrozenxid)) as age
FROM pg_class c
LEFT JOIN pg_class t ON c.reltoastrelid = t.oid
WHERE c.relkind IN ('r', 'm')
ORDER BY age DESC;

#### 6. Сбор статистики по базе данных
ANALYZE собирает статистику о содержимом таблиц в базе данных и сохраняет результаты в системном каталоге pg_statistic. Планировщик запросов использует эту статистику для определения наиболее эффективных планов выполнения запросов.

Синтаксис:

sql
ANALYZE [ ( option [, ...] ) ] [ table_and_columns [, ...] ]
Примеры:

sql
-- Проанализировать всю базу данных
ANALYZE;

-- Проанализировать конкретную таблицу
ANALYZE my_table;

-- Проанализировать конкретные столбцы таблицы
ANALYZE my_table (column1, column2);

-- Проанализировать с подробным выводом
ANALYZE VERBOSE;
Autovacuum и автоанализ:

PostgreSQL настраивается с демоном AUTOVACUUM, который автоматизирует сбор статистики с помощью команд ANALYZE (в дополнение к автоматизации команды VACUUM). Статистику можно собирать по требованию на уровне базы данных, таблицы или столбца.

Условия запуска autovacuum и autoanalyze:

Для обновлений и удалений:

text
Autoanalyze = autovacuum_analyze_scale_factor * tuples + autovacuum_analyze_threshold
Autovacuum = autovacuum_vacuum_scale_factor * tuples + autovacuum_vacuum_threshold
Для вставок (PostgreSQL 13+):

text
Autoanalyze = autovacuum_vacuum_insert_scale_factor * tuples + autovacuum_vacuum_insert_threshold
Значения по умолчанию:

Параметр	Значение
autovacuum_analyze_scale_factor	0.1 (10%)
autovacuum_analyze_threshold	50 строк
autovacuum_vacuum_scale_factor	0.2 (20%)
autovacuum_vacuum_threshold	50 строк
autovacuum_vacuum_insert_scale_factor	0.2 (20%)
autovacuum_vacuum_insert_threshold	1000 строк
Пример расчёта: Для таблицы из 100 строк ANALYZE активируется при изменении 60 строк (0.1 * 100 + 50), а VACUUM — при изменении 70 строк (0.2 * 100 + 50).

Просмотр статистики:

Представление pg_stat_all_tables содержит по одной строке на каждую таблицу в текущей базе данных (включая TOAST-таблицы) со статистикой по обращениям к этой таблице: OID таблицы, схема и имя таблицы, количество инициированных последовательных сканирований, количество живых строк, полученных последовательными сканированиями, количество инициированных индексных сканирований, количество живых строк, полученных индексными сканированиями, количество вставок, обновлений и удалений строк, время последней ручной очистки, время последней очистки демоном autovacuum, время последнего ручного анализа и время последнего анализа демоном autovacuum.

Примеры запросов:

sql
-- Просмотр статистики по конкретной таблице
SELECT relname, last_vacuum, last_autovacuum, vacuum_count, autovacuum_count
FROM pg_stat_all_tables
WHERE relname = 'vacuum_test';

-- Определение таблиц, нуждающихся в очистке
SELECT schemaname, relname, n_live_tup, n_dead_tup,
       n_dead_tup / (n_live_tup + 1) * 100 as bloat_pct,
       last_autovacuum, last_autoanalyze
FROM pg_stat_all_tables
WHERE n_live_tup > 0
ORDER BY n_dead_tup DESC;

#### 7. Практическая работа
##### 7.1. Выполнение обычной очистки
##### Шаг 1. Создать тестовую таблицу:

sql
CREATE TABLE vacuum_test (integer_column integer);

##### Шаг 2. Определить размер таблицы:

sql
SELECT pg_size_pretty(pg_total_relation_size('vacuum_test'));

##### Шаг 3. Вставить данные:

sql
INSERT INTO vacuum_test
SELECT * FROM generate_series(1, 500000);

##### Шаг 4. Проверить размер после вставки:

sql
SELECT pg_size_pretty(pg_table_size('vacuum_test'));

##### Шаг 5. Обновить все строки (создаст мёртвые кортежи):

sql
UPDATE vacuum_test SET integer_column = integer_column + 1;

##### Шаг 6. Проверить размер после обновления:

sql
SELECT pg_size_pretty(pg_table_size('vacuum_test'));

##### Шаг 7. Просмотреть статистику autovacuum:

sql
SELECT relname, last_vacuum, last_autovacuum, vacuum_count, autovacuum_count
FROM pg_stat_all_tables
WHERE relname = 'vacuum_test';

##### Шаг 8. Выполнить ручную очистку:

sql
VACUUM vacuum_test;

##### Шаг 9. Проверить размер после обычной очистки:

sql
SELECT pg_size_pretty(pg_table_size('vacuum_test'));
Обычная очистка не возвращает место операционной системе, но делает его доступным для повторного использования внутри таблицы.

##### 7.2. Очистка большого количества строк
##### Шаг 1. Создать таблицу с большим количеством строк:

sql
CREATE TABLE big_vacuum_test (id serial, data text);
INSERT INTO big_vacuum_test (data)
SELECT md5(random()::text) FROM generate_series(1, 1000000);

##### Шаг 2. Проверить размер таблицы:

sql
SELECT pg_size_pretty(pg_table_size('big_vacuum_test'));

##### Шаг 3. Удалить большое количество строк (например, половину):

sql
DELETE FROM big_vacuum_test WHERE id % 2 = 0;

##### Шаг 4. Проверить статистику:

sql
SELECT relname, n_live_tup, n_dead_tup, n_tup_del
FROM pg_stat_all_tables
WHERE relname = 'big_vacuum_test';

##### Шаг 5. Выполнить очистку с параллельной обработкой индексов:

sql
VACUUM (PARALLEL 4, VERBOSE) big_vacuum_test;

##### Шаг 6. Проверить размер после очистки:

sql
SELECT pg_size_pretty(pg_table_size('big_vacuum_test'));

##### Шаг 7. Проверить статистику после очистки:

sql
SELECT relname, n_live_tup, n_dead_tup
FROM pg_stat_all_tables
WHERE relname = 'big_vacuum_test';

##### 7.3. Полная очистка после удаления большого количества строк
##### Шаг 1. Проверить текущий размер таблицы:

sql
SELECT pg_size_pretty(pg_table_size('big_vacuum_test'));

##### Шаг 2. Выполнить полную очистку (VACUUM FULL):

sql
VACUUM FULL big_vacuum_test;

##### Шаг 3. Проверить размер после полной очистки:

sql
SELECT pg_size_pretty(pg_table_size('big_vacuum_test'));
VACUUM FULL перезаписывает таблицу в новый файл без лишнего пространства, возвращая неиспользуемое место операционной системе. При этом таблица блокируется на время операции.

##### Шаг 4. Выполнить REINDEX для перестроения индексов:

sql
REINDEX TABLE big_vacuum_test;

##### Шаг 5. Выполнить CLUSTER для физического упорядочивания:

sql
-- Сначала создать индекс, если его нет
CREATE INDEX idx_big_vacuum_id ON big_vacuum_test(id);

-- Кластеризовать таблицу по этому индексу
CLUSTER big_vacuum_test USING idx_big_vacuum_id;

##### Шаг 6. Выполнить сбор статистики:

sql
ANALYZE big_vacuum_test;

##### Шаг 7. Проверить итоговое состояние:

sql
SELECT relname, n_live_tup, n_dead_tup, last_vacuum, last_autovacuum
FROM pg_stat_all_tables
WHERE relname IN ('vacuum_test', 'big_vacuum_test');

##### 7.4. Проверка защиты от переполнения счётчика транзакций
##### Шаг 1. Проверить возраст XID для всех таблиц:

sql
SELECT c.oid::regclass as table_name,
       greatest(age(c.relfrozenxid), age(t.relfrozenxid)) as xid_age
FROM pg_class c
LEFT JOIN pg_class t ON c.reltoastrelid = t.oid
WHERE c.relkind IN ('r', 'm')
ORDER BY xid_age DESC
LIMIT 10;

##### Шаг 2. Проверить параметры замораживания:

sql
SHOW vacuum_freeze_min_age;
SHOW vacuum_freeze_table_age;
SHOW autovacuum_freeze_max_age;

##### Шаг 3. Выполнить агрессивную очистку с замораживанием:

sql
VACUUM FREEZE big_vacuum_test;

##### Шаг 4. Проверить возраст XID после замораживания:

sql
SELECT c.oid::regclass as table_name,
       age(c.relfrozenxid) as xid_age
FROM pg_class c
WHERE c.relname = 'big_vacuum_test';
После замораживания возраст XID должен существенно уменьшиться.

##### 7.5. Полная сводка команд практической работы
```sql
-- === 1. Обычная очистка ===
CREATE TABLE vacuum_test (integer_column integer);
INSERT INTO vacuum_test SELECT * FROM generate_series(1, 500000);
UPDATE vacuum_test SET integer_column = integer_column + 1;
VACUUM vacuum_test;
SELECT pg_size_pretty(pg_table_size('vacuum_test'));

-- === 2. Очистка большого количества строк ===
CREATE TABLE big_vacuum_test (id serial, data text);
INSERT INTO big_vacuum_test (data) SELECT md5(random()::text) FROM generate_series(1, 1000000);
DELETE FROM big_vacuum_test WHERE id % 2 = 0;
VACUUM (PARALLEL 4, VERBOSE) big_vacuum_test;

-- === 3. Полная очистка ===
VACUUM FULL big_vacuum_test;
SELECT pg_size_pretty(pg_table_size('big_vacuum_test'));

-- === 4. REINDEX и CLUSTER ===
REINDEX TABLE big_vacuum_test;
CREATE INDEX idx_big_vacuum_id ON big_vacuum_test(id);
CLUSTER big_vacuum_test USING idx_big_vacuum_id;

-- === 5. Сбор статистики ===
ANALYZE big_vacuum_test;

-- === 6. Проверка защиты от переполнения XID ===
SELECT c.oid::regclass, age(c.relfrozenxid) FROM pg_class c WHERE c.relname = 'big_vacuum_test';
VACUUM FREEZE big_vacuum_test;
SELECT c.oid::regclass, age(c.relfrozenxid) FROM pg_class c WHERE c.relname = 'big_vacuum_test';

-- === 7. Просмотр статистики ===
SELECT relname, n_live_tup, n_dead_tup, last_vacuum, last_autovacuum
FROM pg_stat_all_tables
WHERE relname IN ('vacuum_test', 'big_vacuum_test');
```
