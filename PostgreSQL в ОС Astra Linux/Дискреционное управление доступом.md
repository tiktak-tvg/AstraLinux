### Дискреционное управление доступом в СУБД PostgreSQL в Astra Linux Special Edition
#### 1. Дискреционное управление доступом в СУБД PostgreSQL
В составе Astra Linux Special Edition используется СУБД PostgreSQL, доработанная в соответствии с требованием интеграции с ОС в части мандатного управления доступом к информации. Данная ДП-модель описывает все аспекты дискреционного, мандатного и ролевого управления доступом с учётом безопасности информационных потоков.

Основные принципы дискреционного управления доступом:

- На защищаемые именованные объекты устанавливаются базовые правила разграничения доступа (ПРД) в виде идентификаторов номинальных субъектов, которые вправе распоряжаться доступом к данной сущности, и прав доступа к сущности.
- В СУБД PostgreSQL для управления правами на доступ к БД используется концепция ролей — ролевое управление доступом. Под ролью понимается пользователь или группа пользователей БД. Роли могут являться владельцами объектов БД и могут назначать привилегии на управление объектами для других ролей, имеющих доступ к данным объектам.
- Разграничение доступа к операциям на уровне СУБД реализуется применением дискреционных ПРД. Для этого используется право владения объектом и право на создание объектов. Владелец объекта может модифицировать и удалять объект. В общем случае владельцем является создатель объекта или суперпользователь (администратор БД).

Особенности дискреционного управления в PostgreSQL:

- Для каждого объекта явно задаётся список разрешённых для каждого из поименованных субъектов БД (пользователей, групп или ролей) типов доступа (ACL). При разборе запроса к БД осуществляется проверка возможности предоставления доступа субъекта к объекту.
- Дискреционные ПРД применяются после разбора запроса пользователя и построения плана его выполнения.
- Дискреционные ПРД к столбцам объекта применяются только при отсутствии явного разрешения на доступ к самой таблице. Таким образом, права доступа к объекту являются доминирующими.
- Объектами дискреционного управления доступом могут быть столбцы таблицы, поскольку они однозначно идентифицируются по составному имени таблицы и столбца. Отдельная строка таблицы не является однозначно идентифицируемым объектом, и в общем случае дискреционные ПРД к ней применены быть не могут.

#### 2. Привилегии для работы с объектами СУБД
В рамках дискреционных ПРД определены следующие операции над таблицами и хранящимися в них данными:

Привилегия      | Описание
--------------- | ------------------------------------
SELECT	 | Чтение данных из таблицы
INSERT	 | Вставка новых данных в таблицу
DELETE	 | Удаление некоторых/всех данных в таблице
UPDATE	 | Изменение данных в таблице
REFERENCES	 | Использование данных таблицы для внешних ключей
TRIGGER	 | Создание и назначение для таблицы триггеров
TRUNCATE	 | Очистка таблицы (удаление всех данных)

Привилегии для других объектов БД:

Объект          | Описание
--------------- | ------------------------------------
Вид (view)	 | SELECT, INSERT, DELETE, UPDATE (набор операций для таблиц, за исключением создания триггеров и внешних ключей)
Последовательность	 | SELECT (чтение значения счётчика), UPDATE (установка значения), USAGE (выполнение функций манипулирования счётчиком)
База данных	 | CREATE (создание БД), CONNECT (установка соединения), TEMPORARY/TEMP (создание временных таблиц)
Функция	 | EXECUTE (выполнение функции)
Язык	 | USAGE (использование языка для написания функций)
Схема	 | CREATE (создание объектов в схеме), USAGE (использование объектов схемы)
Табличное пространство	 | CREATE (создание объектов)

#### 3. Просмотр списков управления доступом
Для просмотра списков управления доступом (ACL) в PostgreSQL используются следующие команды и представления:

Просмотр прав на объекты:

```sql
-- Просмотр прав на все объекты в текущей базе
\dp

-- Просмотр прав на конкретную таблицу
\dp table_name

-- Просмотр прав на схемы
\dn+

-- Просмотр прав на базы данных
\l+
```
Просмотр через системные каталоги:

```sql
-- Просмотр ACL для таблиц
SELECT relname, relacl FROM pg_class WHERE relkind = 'r';

-- Просмотр ACL для баз данных
SELECT datname, datacl FROM pg_database;

-- Просмотр ACL для схем
SELECT nspname, nspacl FROM pg_namespace;
```
Просмотр информации о ролях:

```sql
-- Список всех ролей
\du

-- Детальная информация о роли
SELECT * FROM pg_roles WHERE rolname = 'username';
```
#### 4. Средства управления дискреционными правами доступа
Для управления дискреционными ПРД к объектам БД СУБД PostgreSQL используется графическая утилита pgAdmin3 (или pgAdmin4 для более новых версий). Для делегирования дискреционных прав доступа к объектам используется команда SQL GRANT, а для отмены — команда REVOKE.

Основные команды:

```sql
-- Предоставление привилегий
GRANT SELECT, INSERT ON table_name TO role_name;

-- Предоставление привилегий с правом передачи
GRANT SELECT ON table_name TO role_name WITH GRANT OPTION;

-- Предоставление привилегий на все таблицы в схеме
GRANT SELECT ON ALL TABLES IN SCHEMA schema_name TO role_name;

-- Отмена привилегий
REVOKE INSERT ON table_name FROM role_name;

-- Отмена всех привилегий
REVOKE ALL ON table_name FROM role_name;
```
Конфигурационные параметры для управления дискреционным доступом:

Параметр        | Описание
--------------- | ------------------------------------
ac_enable_trusted_owner	 | Позволяет администратору запретить владельцам объектов передавать права на доступ к ним другим пользователям СУБД. При значении FALSE распределение прав доступа к объектам БД разрешено только администраторам СУБД
ac_allow_grant_options	 | Позволяет администратору запретить передачу уже имеющихся прав доступа на объект другим ролям. При значении FALSE запрещается использовать команду GRANT с привилегией WITH GRANT OPTION
ac_allow_admin_options	 | Позволяет администратору запретить передачу прав членства роли другим ролям. При значении FALSE запрещается использовать GRANT с привилегией WITH ADMIN OPTION
ac_enable_truncate	 | Позволяет администратору запретить владельцам объектов и пользователям, обладающим правом TRUNCATE, выполнять удаление всех записей из таблиц. При значении FALSE выполнение команды TRUNCATE запрещено всем пользователям

#### 5. Защита на уровне строк (Row Level Security)
Дополнительно для ограничения набора данных, выдаваемых пользователю, можно применять входящую в PostgreSQL систему фильтрации строк (POLICY) под названием ROW LEVEL SECURITY (RLS) — фильтровать строки, выдаваемые из таблицы указанному пользователю (пользователям) на основании вычисления заданного логического выражения.

Включение RLS для таблицы:

```sql
ALTER TABLE table_name ENABLE ROW LEVEL SECURITY;
```
Создание политики:

```sql
CREATE POLICY policy_name ON table_name
    FOR SELECT
    TO role_name
    USING (condition);
```
Принудительное применение RLS для владельца таблицы:

```sql
ALTER TABLE table_name FORCE ROW LEVEL SECURITY;
```
Важно: На владельца таблицы защита строк по умолчанию не действует, хотя он может включить её для себя принудительно, выполнив команду ALTER TABLE ... FORCE ROW LEVEL SECURITY.

#### 6. Конфигурационные параметры для настройки дискреционного доступа
Помимо перечисленных выше параметров (ac_enable_trusted_owner, ac_allow_grant_options, ac_allow_admin_options, ac_enable_truncate), в СУБД PostgreSQL из состава Astra Linux Special Edition существуют и другие параметры, связанные с безопасностью:

Параметр        | Описание
--------------- | ------------------------------------
ac_ignore_socket_maclabel	 | Определяет, будет ли сервер СУБД игнорировать мандатные метки сокетов
ac_session_maclabel	 | Привилегия ОС, используемая в СУБД; может быть изменена (остальные привилегии ОС не могут быть изменены средствами СУБД)
row_security	 | Управляет применением защиты на уровне строк. Установка значения off не отключает защиту строк, но может влиять на поведение системы

#### 7. Практическая работа: автоматизированное тестирование
##### 7.1. Запуск автоматической процедуры тестирования
Для запуска автоматической процедуры тестирования СУБД PostgreSQL необходимо выполнить следующие шаги:

##### Шаг 1. Войти в систему от имени администратора с высокой меткой целостности.

##### Шаг 2. Запустить окно терминала.

##### Шаг 3. Установить пакет тестирования выбранной версии СУБД:

```bash
sudo apt install postgresql-se-test-x.x
```
Например, для PostgreSQL 11:

```bash
sudo apt install postgresql-se-test-11
```
##### Шаг 4. Установить на каталог /tmp необходимые для выполнения тестирования мандатные атрибуты:

```bash
sudo pdpl-file 3:0:-1:ccnr /tmp
```
##### Шаг 5. Перейти в каталог тестов:

```bash
cd /usr/share/postgresql/11/test/pgacext/
```
##### Шаг 6. Запустить тесты:

```bash
sudo ./runtests -all
```
##### Шаг 7. Сбросить мандатные атрибуты каталога /tmp:

```bash
sudo pdpl-file 0 /tmp
```
##### 7.2. Варианты запуска тестов
Скрипт запуска тестов СУБД runtests.sh имеет несколько вариантов запуска:

Опция           | Описание
--------------- | ------------------------------------
-all	 | Запуск всех тестов
-acl	 | Запуск тестов проверки дискреционного управления доступом
-mac	 | Запуск тестов проверки мандатного управления доступом
-f ФАЙЛ	 | Запуск указанного теста
-i ФАЙЛ_СО_СПИСКОМ ОПЦИЙ	 | Запуск только указанных в файле тестов

Пример запуска теста проверки дискреционного управления доступом к базам данных:

```bash
sudo ./runtests -f sql/acl-database.sql
```
Полный список тестов находится в каталоге /usr/share/postgresql/11/test/pgacext/.

##### 7.3. Тесты дискреционного управления доступом
В состав пакета postgresql-se-test-x.x входят тесты дополнительных функциональных возможностей по разграничению доступа. Основные тесты дискреционного управления доступом:

Тест	Описание
acl-database	Проверка дискреционного управления доступом к базам данных
acl-schema	Проверка дискреционного метода контроля доступа к схемам
acl-table	Проверка дискреционного управления доступом к таблицам
acl-column	Проверка дискреционного управления доступом к столбцам объектов БД — заключается в последовательном назначении и отборе прав доступа пользователя к столбцу

При выполнении тестов оценивается соответствие результатов предоставления доступа (успех или отказ) установленным правам пользователя.

##### 7.4. Предоставление привилегий групповой роли
Создание групповой роли и предоставление привилегий:

```sql
-- Создать групповую роль
CREATE ROLE developers;

-- Выдать привилегии групповой роли
GRANT SELECT, INSERT, UPDATE, DELETE ON ALL TABLES IN SCHEMA public TO developers;
GRANT USAGE ON SCHEMA public TO developers;
```
##### 7.5. Проверка привилегий для ролей с INHERIT и NOINHERIT
Создание ролей с разными атрибутами наследования:

```sql
-- Роль с INHERIT (наследует привилегии групповых ролей автоматически)
CREATE ROLE dev_inherit LOGIN INHERIT PASSWORD 'pass1';

-- Роль с NOINHERIT (не наследует привилегии автоматически)
CREATE ROLE dev_noinherit LOGIN NOINHERIT PASSWORD 'pass2';

-- Включить обе роли в групповую роль
GRANT developers TO dev_inherit, dev_noinherit;
```
Проверка наследования привилегий:

Для роли с INHERIT: После подключения к базе данных роль dev_inherit автоматически получает все привилегии, выданные роли developers. Проверка:

```sql
-- Подключиться как dev_inherit
psql -U dev_inherit -d testdb

-- Проверить доступ к таблице (должен быть разрешён)
SELECT * FROM some_table;
```
Для роли с NOINHERIT: Роль dev_noinherit не получает привилегии автоматически. Для использования прав групповой роли необходимо явно переключиться:

```sql
-- Подключиться как dev_noinherit
psql -U dev_noinherit -d testdb

-- Проверить доступ к таблице (должен быть запрещён)
SELECT * FROM some_table;  -- ОШИБКА: permission denied

-- Переключиться на групповую роль
SET ROLE developers;

-- Теперь доступ разрешён
SELECT * FROM some_table;
```
Ключевое различие:

Атрибут	        | Поведение
--------------- | ------------------------------------
INHERIT	 | Роль автоматически использует привилегии всех ролей, членами которых она является (прямо или косвенно). Установлен по умолчанию
NOINHERIT	 | Роль не использует привилегии групповых ролей автоматически. Для доступа необходимо выполнить SET ROLE
