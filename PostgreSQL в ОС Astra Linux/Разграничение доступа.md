#### Дискреционное управление доступом (Discretionary Access Control, DAC)
Это классический механизм, основанный на правах владельца объекта. Владелец (создатель) объекта может самостоятельно предоставлять или отзывать права доступа к нему для других пользователей.
- Субъекты: Роли (Roles) — это пользователи или группы пользователей.
- Объекты: Таблицы, представления, схемы, базы данных, последовательности, функции и т.д.
- Привилегии: Набор разрешённых операций над объектом (SELECT, INSERT, UPDATE, DELETE, TRUNCATE, REFERENCES, TRIGGER и др.).

Инструменты: Для управления правами используются SQL-команды GRANT (предоставить) и REVOKE (отозвать).

Пример:

```sql
-- Предоставить право на чтение и вставку в таблицу books для роли librarian
GRANT SELECT, INSERT ON books TO librarian;

-- Отозвать право на удаление
REVOKE DELETE ON books FROM librarian;
```
#### Ролевое управление доступом (Role-Based Access Control, RBAC)
Роли в PostgreSQL — это центральный элемент управления, объединяющий пользователей и группы. Роль может владеть объектами и иметь атрибуты, определяющие её полномочия.

- Атрибуты ролей: LOGIN (возможность входа), SUPERUSER (суперпользователь), CREATEDB (создание БД), CREATEROLE (создание ролей).
- Членство в ролях: Роли можно объединять в группы. Права, выданные групповой роли, автоматически наследуются её членами (если у роли установлен атрибут INHERIT).

Специальные привилегии: Например, BYPASSRLS позволяет роли игнорировать политики защиты на уровне строк.

Пример:

```sql
-- Создать групповую роль для редакторов
CREATE ROLE editors;

-- Выдать групповой роли права на таблицу
GRANT SELECT, UPDATE ON books TO editors;

-- Создать пользователя и включить его в группу
CREATE ROLE user_editor LOGIN PASSWORD '...';
GRANT editors TO user_editor;
```
#### Мандатное управление доступом (Mandatory Access Control, MAC) в ALSE
Это ключевое отличие защищённой версии PostgreSQL от стандартной. 

Мандатное управление реализовано на основе механизмов безопасности ОС (PARSEC) и использует классификационные метки.
- Метки безопасности: Состоят из иерархического уровня конфиденциальности и набора неиерархических категорий. Они присваиваются как пользователям (субъектам), так и данным (объектам).
- Принцип доминирования: Пользователь может читать данные, если его метка доминирует над меткой данных (уровень пользователя ≥ уровня данных, а категории пользователя включают все категории данных). Запись разрешена, если метка пользователя не выше метки данных.
- Проверка прав: Мандатные права проверяются одновременно с дискреционными. Доступ предоставляется только при разрешении обоих механизмов.
- Контейнеры: Действует правило: метка объекта не может превышать метку контейнера (кластера, БД, табличного пространства, схемы, таблицы), в котором он находится.
- Защита на уровне записей: Для таблиц можно включить защиту на уровне записей. Новые записи наследуют метку безопасности текущего пользователя.
- Настройка: Для включения проверки мандатных меток входящих соединений необходимо установить параметр ac_ignore_socket_maclabel = false в файле postgresql.conf.

#### Защита на уровне строк (Row Level Security, RLS)
Дополнительный механизм, позволяющий фильтровать строки, которые пользователь может видеть или изменять, на основе заданных условий (политик).

- Включение: ALTER TABLE table_name ENABLE ROW LEVEL SECURITY;
- Политики: Создаются командой CREATE POLICY. Условие может проверять текущего пользователя, значения в столбцах и т.д..
- Принцип «запрещено по умолчанию»: Если для таблицы включена RLS, но не создано ни одной политики, доступ к строкам будет полностью заблокирован.

Пример:

```sql
-- Включить RLS на таблице orders
ALTER TABLE orders ENABLE ROW LEVEL SECURITY;

-- Создать политику, позволяющую пользователям видеть только свои заказы
CREATE POLICY user_orders ON orders
    FOR SELECT
    TO PUBLIC
    USING (customer_id = current_user_id());
```
