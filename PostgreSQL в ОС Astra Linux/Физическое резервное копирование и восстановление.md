### Физическое резервное копирование и восстановление в PostgreSQL (Astra Linux Special Edition)
#### 1. Особенности физического резервного копирования
Физическое резервное копирование — это метод создания резервных копий, при котором копируются файлы данных PostgreSQL на уровне файловой системы (каталог PGDATA и все связанные табличные пространства). В отличие от логического копирования (pg_dump), физическое копирование работает с байтовым представлением данных и оперирует на уровне всего кластера.

Ключевые особенности:
- Копирование на уровне файлов — резервная копия представляет собой точную копию файлов кластера: PGDATA, табличных пространств, журналов предзаписи (WAL).
- Физическая резервная копия = байтовая копия через протокол потоковой репликации. Утилита pg_basebackup отправляет команду BASE_BACKUP через соединение libpq replication.
- WAL-архив — основа непрерывного резервного копирования. WAL-архив — это хранилище файлов WAL, которые непрерывно записываются PostgreSQL и архивируются для обеспечения сохранности данных. Без физической базовой копии WAL-архив бесполезен: восстановить кластер PostgreSQL невозможно.
- Преимущества перед логическим: возможность восстановления на определённый момент времени (PITR), копирование всего кластера целиком, более высокая скорость для больших баз.
- Недостатки: копия привязана к конкретной версии PostgreSQL и архитектуре, невозможно выборочное восстановление отдельных таблиц.

Сравнение холодного и горячего резервирования:

Характеристика   | Холодное резервирование  | Горячее резервирование
---------------- | ------------------------ | -------------
Состояние сервера	  | Выключен	 | Работает
Нужны ли WAL	  | Не нужны	 | Нужны за время копирования
Согласованность	 | Гарантирована	  | Требуется восстановление
Время простоя	  | Есть	| Отсутствует

#### 2. Холодное резервное копирование
Холодное резервное копирование (offline backup) — это физическая базовая копия, снятая при остановленном экземпляре PostgreSQL. Такие копии согласованы по определению и представляют собой снимок базы данных на момент её остановки.

Процедура:

```bash
# 1. Остановить кластер PostgreSQL
sudo pg_ctlcluster 15 main stop

# 2. Скопировать каталог данных
sudo cp -a /var/lib/postgresql/15/main /backup/cold_backup_$(date +%Y%m%d)

# 3. Запустить кластер
sudo pg_ctlcluster 15 main start
```
Восстановление из холодной копии:

```bash
# 1. Остановить кластер (если запущен)
sudo pg_ctlcluster 15 main stop

# 2. Удалить повреждённый каталог данных
sudo rm -rf /var/lib/postgresql/15/main

# 3. Восстановить из копии
sudo cp -a /backup/cold_backup_20260919 /var/lib/postgresql/15/main

# 4. Установить права
sudo chown -R postgres:postgres /var/lib/postgresql/15/main

# 5. Запустить кластер
sudo pg_ctlcluster 15 main start
```
> Важно: холодная копия не требует WAL-архива для восстановления, хотя может его использовать при наличии.

#### 3. Горячее резервное копирование
Горячее резервное копирование (online backup) — это физическая базовая копия, снятая с работающего экземпляра PostgreSQL. Такие копии также называют онлайн-копиями.

Особенности:
- Требуется WAL-архив. В горячую копию попадают несогласованные данные. Для восстановления нужны WAL-файлы от последней контрольной точки за всё время копирования файловой системы.
- Параметр wal_level должен быть archive или выше (archive < hot_standby < logical).
- pg_basebackup автоматически переводит сервер в режим резервного копирования и выводит из него. Копия всегда снимается со всего кластера целиком.
Требования для запуска pg_basebackup:

Требование       | Описание  
---------------- | ------------------------ 
Права	 | Суперпользователь или роль с атрибутом REPLICATION
pg_hba.conf	 | Разрешение на подключение к базе replication
max_wal_senders	 | Минимум 1 (2 при использовании --xlog-method=stream)

#### 4. Создание автономной резервной копии с помощью pg_basebackup
pg_basebackup — утилита для создания базовой резервной копии работающего кластера. Копия снимается без влияния на других клиентов базы данных и может использоваться как для восстановления на момент времени (PITR), так и в качестве отправной точки для резервного сервера.

Основные параметры:

Параметр         | Описание  
---------------- | ------------------------ 
-D, --pgdata=каталог	 | Целевой каталог для резервной копии
-F, --format=p|t	 | Формат: plain (по умолчанию) или tar
-X, --wal-method=fetch|stream	 | Метод передачи WAL: fetch (в конце) или stream (в процессе)
-R, --write-recovery-conf	 | Записать настройки восстановления
-P, --progress	 | Показывать прогресс
-v, --verbose	 | Подробный вывод
-h, --host	 | Хост сервера
-p, --port	 | Порт сервера
-U, --username	 | Имя пользователя

Пример создания автономной (базовой) резервной копии:

```bash
# Создание базовой копии в формате plain с потоковой передачей WAL
pg_basebackup -h localhost -p 5432 -U postgres -D /backup/base_$(date +%Y%m%d) -Fp -Xs -P -v -R
```
Восстановление из автономной резервной копии:

```bash
# 1. Остановить кластер
sudo pg_ctlcluster 15 main stop

# 2. Очистить каталог данных
sudo rm -rf /var/lib/postgresql/15/main/*

# 3. Скопировать резервную копию
sudo cp -a /backup/base_20260919/* /var/lib/postgresql/15/main/

# 4. Установить права
sudo chown -R postgres:postgres /var/lib/postgresql/15/main

# 5. Запустить кластер
sudo pg_ctlcluster 15 main start
```
#### 5. Непрерывное архивирование журналов предзаписи
Непрерывное архивирование (continuous archiving) — это механизм, при котором PostgreSQL постоянно копирует заполненные сегменты WAL в архивное хранилище. В сочетании с базовой резервной копией это обеспечивает возможность восстановления на любой момент времени (PITR).

Настройка в postgresql.conf:

```ini
# Включить режим архивирования
wal_level = replica
archive_mode = on
archive_command = 'test ! -f /backup/wal_archive/%f && cp %p /backup/wal_archive/%f'
```
Пояснение параметров:
- wal_level = replica — уровень WAL, достаточный для архивирования и репликации.
- archive_mode = on — включает режим архивирования.
- archive_command — команда оболочки для копирования WAL-сегмента. %p заменяется на путь к файлу, %f — на имя файла.

Важные правила для archive_command:
- Команда должна возвращать нулевой код возврата только при успешном архивировании. При ненулевом коде PostgreSQL будет периодически повторять попытку.
- Команда не должна перезаписывать существующие файлы — это важная мера безопасности.
- Пример с проверкой существования файла: test ! -f /mnt/server/archivedir/%f && cp %p /mnt/server/archivedir/%f.

Создание каталога для архива:

```bash
sudo mkdir -p /backup/wal_archive
sudo chown postgres:postgres /backup/wal_archive
sudo chmod 700 /backup/wal_archive
```
Перезапуск кластера после изменения параметров:

```bash
sudo pg_ctlcluster 15 main restart
```
Проверка работы архивирования:

```bash
# Просмотр архивных WAL-файлов
ls -la /backup/wal_archive/

# Просмотр статистики архиватора
sudo -u postgres psql -c "SELECT * FROM pg_stat_archiver;"
```
#### 6. Создание резервной копии при настроенном непрерывном архивировании
При настроенном archive_mode создание базовой копии выполняется той же утилитой pg_basebackup, но теперь WAL-файлы будут автоматически архивироваться:

```bash
# Создание базовой копии с потоковой передачей WAL
pg_basebackup -h localhost -p 5432 -U postgres -D /backup/base_with_archive_$(date +%Y%m%d) -Fp -Xs -P -v -R
```
Ключевое отличие: в режиме -Xs (stream) WAL-файлы передаются вместе с базовой копией в процессе её создания. Это гарантирует, что в резервной копии будет весь необходимый WAL для восстановления.

#### 7. Восстановление с использованием резервных копий журналов предзаписи
Общая процедура восстановления:
- Остановить кластер.
- Очистить каталог данных.
- Восстановить базовую резервную копию.
- Настроить restore_command для получения WAL из архива.
- Запустить кластер — PostgreSQL начнёт воспроизведение WAL из архива.

Настройка restore_command в postgresql.conf:

```ini
restore_command = 'cp /backup/wal_archive/%f %p'
```
Пример restore_command из практических руководств:

```ini
archive_mode = 'on'
archive_command = 'cp %p /tmp/archive1/%f'
restore_command = 'cp /tmp/archive1/%f %p'
```
Эта пара команд обеспечивает архивирование WAL в /tmp/archive1/ и восстановление из него.

#### 8. Восстановление до определённой точки (PITR)
Point-in-Time Recovery (PITR) — это возможность восстановить базу данных на любой момент времени, начиная с первой доступной базовой копии.

Создание точки восстановления:

```sql
SELECT pg_create_restore_point('my_restore_point');
```
Настройка восстановления в postgresql.conf:

```ini
restore_command = 'cp /backup/wal_archive/%f %p'
recovery_target_name = 'my_restore_point'
recovery_target_action = 'promote'
```
Альтернативные цели восстановления:

Параметр         | Описание  
---------------- | ------------------------ 
recovery_target_name	 | Имя точки восстановления
recovery_target_time	 | Временная метка
recovery_target_xid	 | Идентификатор транзакции
recovery_target_lsn	 | Позиция в WAL

Процедура восстановления до точки:
- Остановить PostgreSQL.
- Восстановить базовую копию (из pg_basebackup).
- Создать файл recovery.signal в каталоге данных:

```bash
sudo touch /var/lib/postgresql/15/main/recovery.signal
```
Настроить restore_command и recovery_target_* в postgresql.conf.

Запустить кластер — PostgreSQL применит WAL до указанной точки и перейдёт в рабочий режим.

#### 9. Практическая работа
##### 9.1. Создание холодной резервной копии
```bash
# Остановить кластер
sudo pg_ctlcluster 15 main stop

# Создать каталог для резервных копий
sudo mkdir -p /backup/cold

# Скопировать каталог данных
sudo cp -a /var/lib/postgresql/15/main /backup/cold/main_$(date +%Y%m%d)

# Запустить кластер
sudo pg_ctlcluster 15 main start

# Проверить
ls -la /backup/cold/
```
##### 9.2. Создание автономной (базовой) резервной копии
```bash
# Создать каталог для базовых копий
sudo mkdir -p /backup/base

# Создать базовую копию с потоковой передачей WAL
sudo -u postgres pg_basebackup -h localhost -p 5432 -D /backup/base/full_$(date +%Y%m%d) -Fp -Xs -P -v -R

# Проверить содержимое
ls -la /backup/base/full_*/
```
##### 9.3. Восстановление из автономной (базовой) резервной копии
```bash
# Остановить кластер
sudo pg_ctlcluster 15 main stop

# Сохранить текущий каталог (на всякий случай)
sudo mv /var/lib/postgresql/15/main /var/lib/postgresql/15/main_old

# Восстановить из копии
sudo cp -a /backup/base/full_20260919 /var/lib/postgresql/15/main

# Установить права
sudo chown -R postgres:postgres /var/lib/postgresql/15/main

# Запустить кластер
sudo pg_ctlcluster 15 main start

# Проверить
sudo -u postgres psql -c "SELECT current_database();"
```
##### 9.4. Настройка файлового архивирования журналов предзаписи
##### Шаг 1. Создать каталог для архива:

```bash
sudo mkdir -p /backup/wal_archive
sudo chown postgres:postgres /backup/wal_archive
sudo chmod 700 /backup/wal_archive
```
##### Шаг 2. Настроить postgresql.conf:

```bash
sudo nano /etc/postgresql/15/main/postgresql.conf
```
Добавить:

```ini
wal_level = replica
archive_mode = on
archive_command = 'test ! -f /backup/wal_archive/%f && cp %p /backup/wal_archive/%f'
```
##### Шаг 3. Перезапустить кластер:

```bash
sudo pg_ctlcluster 15 main restart
```
##### Шаг 4. Проверить работу архивирования:

```bash
# Выполнить несколько транзакций
sudo -u postgres psql -c "CREATE TABLE archive_test (id serial, data text);"
sudo -u postgres psql -c "INSERT INTO archive_test (data) VALUES ('test1'), ('test2');"

# Переключить WAL-сегмент (опционально)
sudo -u postgres psql -c "SELECT pg_switch_wal();"

# Проверить архив
ls -la /backup/wal_archive/

# Проверить статистику архиватора
sudo -u postgres psql -c "SELECT * FROM pg_stat_archiver;"
```
##### 9.5. Создание базовой резервной копии при настроенном потоковом архивировании
```bash
# Создать базовую копию с потоковой передачей WAL
sudo -u postgres pg_basebackup -h localhost -p 5432 -D /backup/base/with_wal_$(date +%Y%m%d) -Fp -Xs -P -v -R

# Проверить, что WAL-файлы включены в копию
ls -la /backup/base/with_wal_*/pg_wal/
```
##### 9.6. Восстановление из базовой резервной копии при настроенном потоковом архивировании
##### Шаг 1. Остановить кластер:

```bash
sudo pg_ctlcluster 15 main stop
```
##### Шаг 2. Очистить каталог данных:

```bash
sudo rm -rf /var/lib/postgresql/15/main/*
```
##### Шаг 3. Восстановить базовую копию:

```bash
sudo cp -a /backup/base/with_wal_20260919/* /var/lib/postgresql/15/main/
sudo chown -R postgres:postgres /var/lib/postgresql/15/main
```
##### Шаг 4. Настроить restore_command:

```bash
sudo nano /var/lib/postgresql/15/main/postgresql.conf
```
Добавить или раскомментировать:

```ini
restore_command = 'cp /backup/wal_archive/%f %p'
```
##### Шаг 5. Создать файл recovery.signal (если требуется восстановление до точки):

```bash
sudo touch /var/lib/postgresql/15/main/recovery.signal
```
##### Шаг 6. Запустить кластер:

```bash
sudo pg_ctlcluster 15 main start
```
##### Шаг 7. Проверить восстановление:

```bash
# Подключиться и проверить данные
sudo -u postgres psql -d postgres -c "SELECT * FROM archive_test;"

# Проверить, что кластер вышел из режима восстановления
sudo -u postgres psql -c "SELECT pg_is_in_recovery();"

Ожидаемый результат: pg_is_in_recovery() возвращает f (false) — кластер работает в обычном режиме.
```
##### 9.7. Полная сводка команд практической работы
```bash
# === 1. Холодная резервная копия ===
sudo pg_ctlcluster 15 main stop
sudo mkdir -p /backup/cold
sudo cp -a /var/lib/postgresql/15/main /backup/cold/main_$(date +%Y%m%d)
sudo pg_ctlcluster 15 main start

# === 2. Автономная (базовая) резервная копия ===
sudo mkdir -p /backup/base
sudo -u postgres pg_basebackup -h localhost -p 5432 -D /backup/base/full_$(date +%Y%m%d) -Fp -Xs -P -v -R

# === 3. Восстановление из автономной копии ===
sudo pg_ctlcluster 15 main stop
sudo mv /var/lib/postgresql/15/main /var/lib/postgresql/15/main_old
sudo cp -a /backup/base/full_20260919 /var/lib/postgresql/15/main
sudo chown -R postgres:postgres /var/lib/postgresql/15/main
sudo pg_ctlcluster 15 main start

# === 4. Настройка архивирования WAL ===
sudo mkdir -p /backup/wal_archive
sudo chown postgres:postgres /backup/wal_archive
sudo chmod 700 /backup/wal_archive
# В postgresql.conf:
#   wal_level = replica
#   archive_mode = on
#   archive_command = 'test ! -f /backup/wal_archive/%f && cp %p /backup/wal_archive/%f'
sudo pg_ctlcluster 15 main restart

# === 5. Базовая копия с потоковым архивированием ===
sudo -u postgres pg_basebackup -h localhost -p 5432 -D /backup/base/with_wal_$(date +%Y%m%d) -Fp -Xs -P -v -R

# === 6. Восстановление из базовой копии с потоковым архивированием ===
sudo pg_ctlcluster 15 main stop
sudo rm -rf /var/lib/postgresql/15/main/*
sudo cp -a /backup/base/with_wal_20260919/* /var/lib/postgresql/15/main/
sudo chown -R postgres:postgres /var/lib/postgresql/15/main
# В postgresql.conf добавить: restore_command = 'cp /backup/wal_archive/%f %p'
sudo pg_ctlcluster 15 main start
sudo -u postgres psql -c "SELECT pg_is_in_recovery();"
```
