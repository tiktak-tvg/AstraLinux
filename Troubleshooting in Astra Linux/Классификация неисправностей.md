### Классификация неисправностей, их диагностика и устранение в Astra Linux
#### 1. Классификация неисправностей, вызвавших нештатную ситуацию
Нештатная ситуация — это любое отклонение работы системы от штатного режима, приводящее к снижению доступности, производительности или нарушению целостности данных. Для эффективной диагностики важно правильно классифицировать причину сбоя.

Основные категории неисправностей:

Категория           | Источник                  | Примеры
------------------- | ------------------------- | ----------------------------
Аппаратные	 | Физические компоненты	  | Отказ диска, перегрев CPU, сбой ОЗУ, неисправность сетевой карты, проблемы с БП
Программные  | (системные)	ОС, драйверы, приложения	  | Ошибки ядра, повреждение файловой системы, конфликты библиотек, утечки памяти
Сетевые	 | Сетевые интерфейсы, протоколы	  | Обрыв канала, потери пакетов, ошибки DNS, конфликт IP, отказ маршрутизации
Вызванные действиями пользователей	 | Ошибки администратора или пользователя	  | Неверная правка конфигурации, случайное удаление файлов, неверные права доступа

В подсистеме безопасности	PARSEC, мандатный доступ	Ошибка меток безопасности, блокировка мандатным контролем, сбои аудита

Признаки, указывающие на категорию:
- Аппаратные: внезапные перезагрузки, ошибки в dmesg, I/O errors, шум/перегрев.
- Программные: зависания процессов, ошибки в логах приложений, kernel panic, повреждение конфигов.
- Сетевые: недоступность узлов, высокий ping, потери пакетов, ошибки резолвинга.
- Пользовательские: «вчера работало», изменения перед сбоем, ошибки прав.
- Безопасности: отказ в доступе с сообщениями PARSEC, ошибки pdp-*, блокировки аудита.

#### 2. Документирование и фиксация изменений в системе
Без фиксации изменений диагностика превращается в угадывание. Основные принципы:
- Ведите журнал изменений: дата, время, автор, что изменено, зачем.
- Перед изменениями: сохраняйте резервные копии конфигов (cp file file.bak.$(date +%F)).
- Используйте системы контроля версий для критичных конфигов (etckeeper, git).
- Фиксируйте состояние до и после изменений (pcs status, ip a, ss -tulnp).
- Документируйте инциденты: симптом, гипотеза, действие, результат.

Пример фиксации:

```text
Дата: 2026-09-20 14:30
Автор: admin
Изменение: правка /etc/network/interfaces — смена IP eth0
Причина: миграция в новую подсеть
Результат: сеть работает, проверено ping/traceroute
Откат: cp /etc/network/interfaces.bak.2026-09-20 /etc/network/interfaces
```
#### 3. Сбор информации об аппаратных и программных компонентах
Аппаратные компоненты:

Инструмент          | Назначение
------------------- | -------------------------
lscpu	              | Информация о процессоре
lsblk, fdisk -l	    | Список дисков и разделов
lspci, lsusb	      | Устройства PCI и USB
dmidecode	          | Информация BIOS/SMBIOS (RAM, материнская плата)
smartctl	          | Состояние SMART жёстких дисков
sensors	            | Температура, вентиляторы, напряжение
free -h	            | Использование ОЗУ
dmesg	              | Сообщения ядра о железе

Программные компоненты:

Инструмент          | Назначение
------------------- | -------------------------
uname -a	 | Версия ядра
cat /etc/astra_version	 | Версия Astra Linux
dpkg -l	 | Установленные пакеты
systemctl list-units --failed	 | Упавшие службы
apt list --upgradable	 | Доступные обновления

Пример сбора общей картины:

```bash
# Собрать сводку в один файл
{
  echo "=== Система ==="; uname -a; cat /etc/astra_version
  echo "=== CPU ==="; lscpu | head -20
  echo "=== RAM ==="; free -h
  echo "=== Диски ==="; lsblk; df -h
  echo "=== Сеть ==="; ip a; ip r
  echo "=== Службы (failed) ==="; systemctl --failed
  echo "=== Последние ошибки ==="; journalctl -p err -b | tail -50
} > /tmp/diag_$(date +%F_%H%M).txt
```
#### 4. Методология поиска и решения неисправностей
Пошаговый алгоритм:
- Сбор информации. Что именно не работает? Когда началось? Что менялось? Кто заметил?
- Локализация. Определить уровень: железо → ОС → сеть → приложение → пользователь.
- Воспроизведение. Попытаться повторить проблему в контролируемых условиях.
- Формулирование гипотезы. На основе симптомов и логов.
- Проверка гипотезы. Минимальное изменение → наблюдение результата.
- Устранение. Применить исправление, зафиксировать.
- Проверка. Убедиться, что проблема решена и не появилось побочных эффектов.
- Документирование. Записать причину, решение, меры предотвращения.

Принципы диагностики:
- От простого к сложному: сначала проверьте кабель и питание, потом логи.
- Одно изменение за раз: не меняйте несколько параметров одновременно.
- Ищите первопричину, а не симптом: перезапуск службы лечит симптом, а не причину.
- Правило «что изменилось?»: 90% сбоев связаны с недавними изменениями.
- Изоляция: отключите подозрительные компоненты, чтобы локализовать проблему.

#### 5. Анализ системной информации в терминале и журнальных файлах
Основные источники журналов:

Источник            | Что содержит
------------------- | -------------------------
journalctl	 | Единый журнал systemd (все службы)
/var/log/syslog	 | Системные сообщения
/var/log/auth.log	  | Аутентификация, sudo, SSH
/var/log/kern.log	  | Сообщения ядра
/var/log/dpkg.log	  | Установка/удаление пакетов
/var/log/apt/history.log	  | История apt
/var/log/audit/audit.log	  | Аудит безопасности (PARSEC)
/var/log/parsec/	  | Логи подсистемы безопасности

*Полезные команды journalctl:*

```bash
# Ошибки текущей загрузки
journalctl -p err -b

# Логи конкретной службы
journalctl -u apache2 -f

# За период
journalctl --since "2026-09-20 10:00" --until "2026-09-20 12:00"

# По конкретному процессу
journalctl _PID=1234

# Ядро
journalctl -k
```
*Анализ в терминале:*

```bash
# Поиск ошибок
grep -i error /var/log/syslog | tail -50

# Отслеживание в реальном времени
tail -f /var/log/syslog /var/log/auth.log

# Подсчёт ошибок
journalctl -p err -b | wc -l
```
#### 6. Основные инструменты диагностики
##### 6.1. Процессы и нагрузка
*ps — снимок процессов:*

```bash
ps aux                    # все процессы
ps -ef --forest           # дерево процессов
ps -eo pid,ppid,cmd,%mem,%cpu --sort=-%mem | head   # топ по памяти
```
*top / htop — интерактивный мониторинг:*

```bash
top -b -n 1 | head -20    # пакетный режим
# В top: P — сортировка по CPU, M — по памяти, k — kill процесса
```
##### 6.2. Память
*free — использование ОЗУ:*

```bash
free -h                   # в человеком читаемом виде
free -m                   # в мегабайтах
```
Интерпретация: столбец available — реально доступная память, а не free.

##### 6.3. Дисковая подсистема
df — использование файловых систем:

```bash
df -h                     # в человекочитаемом виде
df -i                     # inodes
df -hT                    # с типом ФС
```
*iostat — статистика ввода-вывода:*

```bash
iostat -x 2 5             # расширенная статистика каждые 2 с, 5 раз
```
Ключевые показатели: %util (загрузка диска), await (время ожидания), r/s, w/s.

*vmstat — виртуальная память и CPU:*

```bash
vmstat 2 5                # каждые 2 с, 5 раз
```
Ключевые столбцы: r (очередь CPU), si/so (swap in/out), wa (ожидание I/O).

*sar — историческая статистика (пакет sysstat):*

```bash
sar -u 1 5                # CPU
sar -r 1 5                # память
sar -d 1 5                # диски
sar -n DEV 1 5            # сетевые интерфейсы
```
##### 6.4. Сетевые инструменты
ping — проверка доступности:

```bash
ping -c 4 8.8.8.8
ping -I eth0 192.168.1.1  # через конкретный интерфейс
```
*traceroute — маршрут до узла:*

```bash
traceroute 8.8.8.8
traceroute -n 8.8.8.8     # без резолвинга имён
```
*dig — диагностика DNS:*

```bash
dig ya.ru
dig @8.8.8.8 ya.ru A
dig -x 8.8.8.8            # обратный запрос
dig ya.ru MX
```
nslookup — простой DNS-запрос:

```bash
nslookup ya.ru
nslookup ya.ru 8.8.8.8
```
*ss — сокеты (замена netstat):*

```bash
ss -tulnp                 # слушающие порты с процессами
ss -tan                   # все TCP-соединения
ss -s                     # сводка
ss -tnp state established # установленные соединения
```
*netstat — устаревший, но иногда используемый:*

```bash
netstat -tulnp
netstat -rn               # таблица маршрутизации
```
*ip — управление сетью (замена ifconfig/route):*

```bash
ip a                      # адреса
ip r                      # маршруты
ip n                      # ARP-таблица
ip -s link                # статистика интерфейсов
ip link set eth0 up
```
*nmcli — управление NetworkManager:*

```bash
nmcli device status
nmcli connection show
nmcli connection show "Wired connection 1"
nmcli device show eth0
```
*nmap — сканирование сети:*

```bash
nmap 192.168.1.0/24       # обнаружение хостов
nmap -sT 192.168.1.1      # TCP-сканирование
nmap -p 22,80,443 192.168.1.1
nmap -sV 192.168.1.1      # определение версий служб
```
*tcpdump — захват пакетов:*

```bash
tcpdump -i eth0 -n
tcpdump -i eth0 port 80 -w /tmp/http.pcap
tcpdump -i any host 192.168.1.1
tcpdump -i eth0 -nn 'tcp[tcpflags] & tcp-syn != 0'  # только SYN
```
#### 7. Примеры диагностики по категориям
##### 7.1. Аппаратная неисправность
Симптом: система периодически перезагружается.

```bash
# Проверка температуры и питания
sensors
# Проверка ошибок ядра
dmesg | grep -i -E "error|fail|mce|thermal"
# SMART дисков
sudo smartctl -a /dev/sda | grep -i -E "health|error"
# Проверка ОЗУ
sudo memtester 1G 1
```
##### 7.2. Программная неисправность
Симптом: служба не запускается.

```bash
systemctl status apache2
journalctl -u apache2 -n 50
apache2ctl configtest
systemctl list-units --failed
```
##### 7.3. Сетевая неисправность
Симптом: нет доступа к внешнему сайту.

```bash
# 1. Проверка интерфейса
ip a; ip r
# 2. Проверка шлюза
ping -c 2 192.168.1.1
# 3. Проверка DNS
dig @8.8.8.8 ya.ru
# 4. Проверка внешнего адреса
ping -c 2 8.8.8.8
# 5. Трассировка
traceroute 8.8.8.8
# 6. Захват трафика
sudo tcpdump -i eth0 -n host 8.8.8.8
```
##### 7.4. Неисправность, вызванная действиями пользователя
Симптом: после правки конфига не работает SSH.

```bash
# Проверка синтаксиса
sshd -t
# Просмотр последних изменений
ls -la /etc/ssh/sshd_config*
diff /etc/ssh/sshd_config.bak /etc/ssh/sshd_config
# Проверка логов
journalctl -u ssh -n 50
# Проверка порта
ss -tlnp | grep ssh
```
##### 7.5. Неисправность в подсистеме безопасности
Симптом: пользователь не может получить доступ к данным.

```bash
# Проверка метки пользователя
pdpl-user -i username
# Проверка метки файла
pdp-ls -M /path/to/file
# Проверка аудита
sudo tail -f /var/log/audit/audit.log
# Проверка PARSEC
journalctl -u parsec -n 50
```
