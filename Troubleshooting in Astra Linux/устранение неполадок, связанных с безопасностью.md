### Устранение неполадок, связанных с безопасностью ОС Astra Linux
#### 1. Восстановление потерянных паролей
Восстановление доступа зависит от того, известен ли пароль загрузчика GRUB2 и какая учётная запись заблокирована.

##### 1.1. Восстановление пароля администратора (пароль GRUB2 известен)
Если пароль загрузчика известен, можно загрузиться в однопользовательский режим через редактирование параметров загрузки:
- Перезагрузите машину и дождитесь появления меню GRUB2.
- Нажмите клавишу e для редактирования.
- На запрос имени пользователя введите root.
- Введите пароль загрузчика, заданный при установке ОС.
- В строке, начинающейся со слова linux, удалите ro quiet splash и допишите в конец init=/bin/bash.
- Нажмите F10 и дождитесь приглашения root@(none):/#.
- Перемонтируйте файловую систему в режим чтения-записи: mount -o rw,remount /.
- Сбросьте счётчик неудачных попыток входа: faillog -r.
- Смените пароль пользователя: passwd <имя_пользователя> и введите новый пароль.
- Перезагрузите машину: /sbin/reboot -f.

##### 1.2. Восстановление пароля, если пароль GRUB2 неизвестен
Используется установочный диск Astra Linux:
- Загрузитесь с установочного диска и выберите «Режим восстановления».
- Выберите устройство, используемое в качестве корневой системы (например, /dev/sda1).
- Запустите оболочку в этом разделе.
- Перейдите в терминал (Ctrl+Alt+F2), нажмите Enter для активации консоли.
- Выполните chroot /target.
- Сбросьте счётчик: faillog -r или для доменных пользователей: ``faillog -u user@domain.ru -r``.
- Смените пароль: passwd <имя_пользователя>.
- Выйдите из chroot (exit) и перезагрузите машину (reboot).

##### 1.3. Восстановление пароля обычным пользователем
Пользователь может сменить свой пароль, если он его помнит:

```bash
passwd
```
Система запросит текущий пароль, затем новый и его подтверждение. Если пароль забыт, пользователь должен обратиться к администратору, который задаст новый пароль командой passwd <имя_пользователя> от имени root.

##### 1.4. Разблокировка учётной записи администратора
Если администратор самостоятельно заблокировал свою учётную запись:

Загрузитесь в режиме восстановления.

Выполните: usermod -e "" <имя_пользователя>, где "" — две двойные кавычки, означающие снятие срока действия учётной записи.

##### 1.5. Сброс блокировки через faillock
Для сброса счётчика неудачных попыток входа используется утилита faillock:

```bash
# Просмотр текущего счётчика
faillock --user <имя_пользователя>

# Сброс счётчика
faillock --user <имя_пользователя> --reset

# Или через sudo
sudo faillock --user <имя_пользователя> --reset
```
#### 2. Устранение ошибок при входе пользователя
##### 2.1. Диагностика через journalctl
При проблемах с входом в графическую сессию проверьте журнал systemd:

```bash
# Просмотр ошибок systemd-logind
journalctl -u systemd-logind -b

# Поиск ошибок, связанных с pdpl_text
journalctl -b | grep -i pdpl

# Общий просмотр ошибок текущей загрузки
journalctl -p err -b
```
Типичная проблема: после обновления ОС до Astra Linux SE 1.8 Update 5 в журнале могут появляться строки:

```text
systemd[1]: Failed to start systemd-logind.service - User Login Management.
systemd-logind[1158]: Assertion 'pdpl_text' failed at src/login/logind.c:349
```
Это связано с проверкой linger пользователей. Решение — проверка и настройка linger-сессий для пользователей.

##### 2.2. Проверка служб, связанных с аутентификацией
```bash
# Статус systemd-logind
systemctl status systemd-logind

# Статус SSSD (если используется домен)
systemctl status sssd

# Проверка journalctl по SSSD
journalctl -u sssd -f
```
##### 2.3. Журналы аутентификации
Все факты начала и окончания работы пользователя фиксируются в журнале /var/log/auth.log. Также информация попадает в журнал подсистемы безопасности PARSEC: /var/log/parsec/user.mlog.

```bash
# Просмотр последних событий аутентификации
tail -50 /var/log/auth.log

# Поиск неудачных попыток входа
grep "Failed password" /var/log/auth.log

# Просмотр журнала PARSEC
tail -50 /var/log/parsec/user.mlog
```
##### 2.4. Проверка наличия пользователя в системе
```bash
# Проверка пользователя через getent
getent passwd <имя_пользователя>

# Проверка через id
id <имя_пользователя>

# Если информация не выводится — проверить SSSD
journalctl -u sssd -b
```
Если команды getent или id не выводят информации о пользователе, проверьте журналы SSSD в /var/log/sssd/.

#### 3. Решение проблем с настройками SUDO
##### 3.1. Запрос пароля при каждом вызове sudo
По умолчанию в Astra Linux пароль при вызове sudo может не запрашиваться (настроено NOPASSWD). Для включения запроса пароля:

Через графический инструмент:

```bash
fly-admin-smc
# Политика безопасности → Управление вводом пароля для sudo → Включить
```
Через командную строку:

```bash
sudo astra-sudo-control enable
```
Внесением изменений в конфигурацию:

Отредактируйте файл /etc/sudoers только через visudo:

```bash
sudo visudo
```
Удалите NOPASSWD: из строки:

```text
%astra-admin ALL=(ALL:ALL) ALL
```
Для запрета запоминания пароля добавьте:

```text
Defaults timestamp_timeout=0
```
##### 3.2. Проблема накопления faillog при использовании sudo
При неудачных вызовах sudo с паролем может накапливаться faillog, что приводит к блокировке. Для обхода этой проблемы добавьте в файл /etc/pam.d/sudo вызов pam_tally:

```bash
# Добавить в /etc/pam.d/sudo
auth required pam_tally2.so deny=5 unlock_time=300
```
##### 3.3. Пользователь не может выполнять sudo
Диагностика:

```bash
# Проверить, входит ли пользователь в группу astra-admin
groups <имя_пользователя>

# Проверить настройки sudoers
sudo visudo -c

# Проверить права на файл
sudo -l -U <имя_пользователя>
```
Решение: добавьте пользователя в группу astra-admin:

```bash
sudo usermod -aG astra-admin <имя_пользователя>
```
##### 3.4. Проверка синтаксиса sudoers
```bash
# Проверка синтаксиса без сохранения
sudo visudo -c

# Просмотр текущих правил для пользователя
sudo -l -U <имя_пользователя>
```
#### 4. Решение проблем с доступом к файлам и каталогам
##### 4.1. Диагностика прав доступа
```bash
# Просмотр прав на файл
ls -l /path/to/file

# Просмотр прав на каталог
ls -ld /path/to/directory

# Проверка владельца и группы
stat /path/to/file

# Просмотр расширенных атрибутов
lsattr /path/to/file
```
##### 4.2. Восстановление прав доступа
```bash
# Изменение владельца
sudo chown user:group /path/to/file

# Рекурсивное изменение владельца
sudo chown -R user:group /path/to/directory

# Изменение прав
sudo chmod 755 /path/to/file
sudo chmod -R 644 /path/to/directory
```
##### 4.3. Проблемы с доступом к домашнему каталогу
```bash
# Проверка прав на домашний каталог
ls -ld /home/<имя_пользователя>

# Корректные права: владелец — пользователь, группа — пользователь, права 750 или 700
sudo chown -R user:user /home/user
sudo chmod 750 /home/user
```
#### 5. Решение проблем с дискреционными правами доступа (ACL)
Astra Linux поддерживает списки управления доступом (ACL) для файловых объектов на уровне ядра. ACL работают с файловыми системами ext4, Btrfs, ext2, ext3.

##### 5.1. Проверка текущих ACL
```bash
# Просмотр ACL файла
getfacl /path/to/file

# Просмотр ACL каталога
getfacl /path/to/directory
```
Пример вывода:

```text
# file: /path/to/file
# owner: user
# group: user
user::rw-
user:john:r--
group::r--
mask::r--
other::r--
```
##### 5.2. Установка ACL
```bash
# Предоставить пользователю john права на чтение
setfacl -m u:john:r /path/to/file

# Предоставить группе developers права на чтение и запись
setfacl -m g:developers:rw /path/to/file

# Установить ACL по умолчанию для каталога
setfacl -d -m u:john:rwx /path/to/directory

# Рекурсивная установка ACL
setfacl -R -m u:john:rx /path/to/directory
```
##### 5.3. Удаление ACL
```bash
# Удалить ACL для конкретного пользователя
setfacl -x u:john /path/to/file

# Удалить все ACL
setfacl -b /path/to/file
```
##### 5.4. Маска ACL
Маска ACL ограничивает максимальные права, которые могут быть предоставлены именованным пользователям и группам:

```bash
# Установить маску
setfacl -m m::rx /path/to/file

# Проверить маску
getfacl /path/to/file
```
##### 5.5. Типичные проблемы с ACL

Ошибка              | Причина                   | Решение
------------------- | ------------------------- | -------------------------
Operation not supported	 | Файловая система не поддерживает ACL	 | Перемонтировать с опцией acl или использовать ext4
ACL не применяется	 | Маска ограничивает права	 | Проверить и скорректировать маску через ``setfacl -m m::...``
ACL не наследуется	 | Не установлены ACL по умолчанию	 | Установить: ``setfacl -d -m u:user:rwx /dir``

#### 6. Решение проблем с мандатными правами доступа
Мандатное управление доступом (МРД) — ключевой механизм безопасности Astra Linux Special Edition. Проблемы с доступом часто связаны с неверными мандатными метками.

##### 6.1. Проверка состояния подсистемы PDP
```bash
# Проверка сервиса PDP
systemctl status pdp

# Проверка текущего режима
pdpctl get-mode
# Ожидаемый вывод: enforcing
```
Если режим disabled или permissive:

```bash
sudo pdpctl set-mode enforcing
sudo systemctl restart pdp
```
##### 6.2. Проверка загрузки модулей ядра
```bash
# Проверка установленных компонентов
dpkg -l | grep -E "pdp-tools|parsec|astra-mac"

# Проверка загрузки модуля ядра
lsmod | grep parsec

# Если модуль не загружен:
sudo modprobe parsec
sudo systemctl enable --now pdp
```
##### 6.3. Проверка поддержки xattr
Мандатные метки хранятся в расширенных атрибутах (xattr):

```bash
# Проверка монтирования с xattr
mount | grep -E "^/dev" | grep -v "no_xattr"

# Если xattr не поддерживается, перемонтировать
sudo mount -o remount,xattr /

# Для постоянного применения добавить xattr в /etc/fstab
```
##### 6.4. Просмотр мандатных меток
```bash
# Просмотр меток файла
pdpl-file --get /path/to/file

# Или через ls -Z (если установлен пакет с метками)
ls -Z /path/to/file

# Просмотр меток пользователя
pdpl-user <имя_пользователя>

# Просмотр меток каталога с мандатным контекстом
pdp-ls -Md /share
```
##### 6.5. Назначение мандатных атрибутов пользователям
```bash
# Просмотр доступных уровней и категорий
pdpctl list-levels
pdpctl list-categories

# Назначение атрибутов пользователю
sudo usermod \
  --mac-confidentiality=3 \
  --mac-integrity=2 \
  --mac-categories=1,3 \
  user1

# Проверка
getent passwd user1 | grep mac
# или
pdpctl get-user-attr user1
```
##### 6.6. Назначение мандатных атрибутов файлам и каталогам
```bash
# Установка меток через pdpl-file
sudo pdpl-file \
  --set-confidentiality=3 \
  --set-integrity=2 \
  --set-categories=1,3 \
  /path/to/file_or_dir

# Проверка
pdpl-file --get /path/to/file_or_dir
```
> Важно: для каталогов опция -R применяется только если все вложенные объекты поддерживают xattr. На файловых системах без xattr (FAT, exFAT, NTFS, некоторые сетевые ФС) команда завершится ошибкой Operation not supported.

##### 6.7. Типичные ошибки мандатного доступа и их решения

Ошибка              | Причина                   | Решение
------------------- | ------------------------- | -------------------------
Operation not permitted	 | Недостаточно прав	  | Запускать от root или через sudo
Invalid confidentiality level	  | Уровень не определён в профиле PDP	  | Проверить pdpctl list-levels или отредактировать /etc/pdp/pdp.conf
PDP is disabled	 | Сервис не запущен или отключён	  | systemctl enable --now pdp
Каталог не монтируется в сессии выше «Несекретно»	  | Неверные мандатные права	 | Проверить pdp-ls -Md /share, назначить права: pdpl-file 3:0:0:ccnr /share

##### 6.8. Проблемы с мандатным разграничением в Samba
При работе с общими каталогами Samba в сессии выше «Несекретно» монтирование может не происходить. Необходимо проверить мандатное разграничение доступа на общем каталоге:

```bash
pdp-ls -Md /share
```
Для монтирования каталога под уровнем требуется назначить мандатные права, например:

```bash
sudo pdpl-file 3:0:0:ccnr /share
```

#### 8. Комплексный пример диагностики
Симптом: после обновления пользователь не может войти в графическую сессию, отображается окно ввода атрибутов безопасности, после чего снова появляется экран входа.

Диагностика:

```bash
# 1. Проверить журнал systemd-logind
journalctl -u systemd-logind -b

# 2. Проверить наличие ошибок pdpl_text
journalctl -b | grep -i pdpl

# 3. Проверить статус службы
systemctl status systemd-logind

# 4. Проверить linger для пользователя
loginctl show-user <имя_пользователя> | grep Linger

# 5. Проверить права на домашний каталог
ls -ld /home/<имя_пользователя>
```
Решение:

```bash
# Отключить linger для пользователя (если проблема связана с ним)
sudo loginctl disable-linger <имя_пользователя>

# Перезапустить systemd-logind
sudo systemctl restart systemd-logind

# Проверить, что служба запущена
systemctl status systemd-logind

# Попробовать войти снова
```
